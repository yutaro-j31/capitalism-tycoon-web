## 1. プロジェクトの前提知識（実装担当者向け）

### 1.1 決定論（RNGの扱い）

このゲームは同じシード値・同じ操作列なら必ず同じ結果になる「決定論」を
設計原則としている。`Math.random()` を新規に呼び出してはいけない。
乱数が必要な場合は、既存のハッシュベースの決定論的関数を使う。

参考実装（`js/ma-deal-room.js` にある例）:

```js
function hash(parts){let h=2166136261;String(parts.join('|')).split('').forEach(c=>{h^=c.charCodeAt(0);h=Math.imul(h,16777619);});return h>>>0;}
function unit(...p){return hash(p)/4294967295;}       // 0〜1の一様乱数（決定論的）
function between(a,b,...p){return a+(b-a)*unit(...p);} // a〜bの一様乱数（決定論的）
```

`unit()` / `between()` に渡す引数（`...p`）は「何に対する乱数か」を一意に
特定できる値（週番号・店舗ID・業種IDなど）にする。同じ引数なら常に同じ
乱数値が返る。

**この原則を守れているかの確認方法:** 同じ操作列を2回実行して、
結果（企業価値・現金など）が完全に一致するかを確認する。

### 1.2 テスト・検証環境

`tests/harness.js` を使うと、UIを介さず `TycoonEngine` を直接動かして
週送りのシミュレーションができる。既存の計測スクリプト
`founding-profitability-measure2.js`（このリポジトリに存在する）がこの
手法で書かれているので、参考にすること。

**ジムの実装（§6）で、この手法を回帰テスト（開店後8週間の実測）にまで
発展させている。コンビニ・不動産仲介・成長率底上げの検証も、同じ枠組みを
使って形式を揃えること。**

### 1.3 productionコードとは

`js/` 配下の実際にゲームが動かすコード全体を指す。今回の作業は主に
`js/engine.js`（店舗の収益計算・週次処理）と `js/data.js`（業種ごとの
定数: storeCost・家賃係数・客単価・変動費率など）が対象になる見込み。
ジムの実装では `js/engine.js` の出店見積り・出店処理と、既存の銀行融資
まわり（財務台帳・借入履歴・信用スコア）に接続する形で対応された。

## 3. 残っている2つの構造的バグ（成長率の底上げより先に直す）

**重要: 底上げは「速く育つようにする」話だが、この2つは「育つ前に壊れる」話。**
先に壊れない状態にしないと、成長率をいくら底上げしても壊れるまでの時間が
縮むだけになる。**この2つを直さないまま成長率だけ底上げする作業は行わないこと。**

### 3.1 コンビニ: 多店舗展開すると収益性が悪化する

**原因（実測で特定済み）:** 変動費率が60.4%と4業種の中で突出して高く
（粗利率が薄い）、標準的な拡張判断（トラフィックが高い立地から順に
テナントを選ぶ）を続けていくと、店舗数が増えるほど残っているテナントの
トラフィックが低くなる。同じ変動費構造のまま売上だけが目減りしていくため、
単店では黒字でも多店舗展開すると平均収益性が悪化し、最終的に全体が
赤字化する。

**修正方針:** 変動費率そのものを見直すか、出店する店舗数が増えるにつれて
低トラフィック立地による悪化を緩和する仕組み（例: 店舗数に応じた
仕入れ効率の改善、ブランド力による集客の下支えなど）を入れるか。
実装しやすい方針で対応してよい。

### 3.2 不動産仲介: 資金繰りが確率的に破綻する

**原因（実測で特定済み）:** 不動産仲介の売上（案件成約による手数料収入）は
確率的で、週によって数件成約することもあればゼロのこともある。1件あたりの
手数料は数百万〜数千万円と大きく、**キャッシュフローの分散が非常に大きい。**
一方で家賃・人件費などの固定費は成約の有無に関わらず毎週確実に発生する。
標準的な拡張判断は「直近が黒字なら出店する」というものだが、これは
「谷間の週群を乗り切るための現金バッファが必要」という点を考慮しておらず、
店舗を増やした結果、たまたま成約が続かない週群で現金が尽きて
**倒産（`gameOver` 状態になる）。** 実測では第100週前後で発生した。

**修正方針:** 案件成約の分散（ばらつき）を抑える、店舗ごとに現金バッファを
別途持たせる、または拡張判断のロジック側に「現金バッファが一定週数分
確保されているか」という安全マージンの確認を入れる。実装しやすい方針で
対応してよい。

## 4. 成長率の底上げ目標

### 4.1 目標週数の設定根拠

ラーメンの現状の実測（500週で開始時0.017億円相当→10.20億円、
実効年間成長率94.5%）を基準に、目標週数ごとに必要な成長率倍率を逆算した。

| 目標週数 | 年数 | 必要年間成長率 | 現状比の倍率 |
|---|---|---|---|
| 100週 | 1.9年 | 2684%/年 | 14.3倍（非現実的） |
| 150週 | 2.9年 | 819%/年 | 4.7倍 |
| **200週** | **3.8年** | **428%/年** | **2.7倍** |
| **300週** | **5.8年** | **203%/年** | **1.56倍** |

**採用する目標: ラーメンが標準プレイで200〜300週の範囲で企業価値10億円に
到達するよう、成長率を現状比1.56〜2.7倍に底上げする。**

目標を範囲で持たせているのは、この倍率が店舗経営の複利的な拡大
（出店ペースと利益率の両方の影響を受ける）から逆算した目安であり、
実際に週次エンジンで動かしながら再較正が必要なため。目標週数200〜300週の
どこに実際に着地するかは、実装を見てから確定してよい。

### 4.2 他の3業種の扱い（重要な方針）

**全業種を同じ到達週数に揃えないこと。** 業種ごとの性格の違い
（早く育つが頭打ちが早い、遅いが安定している、など）を保ったまま、
全体を底上げする。

目安:

- **ラーメン**: 200〜300週で10億円到達（基準）
- **ジム**: §6の開業ローンで開店可能になった。開業直後の資金繰りは
  厳しいが、軌道に乗れば単店の稼ぐ力がラーメンより高い、という性格を
  保つ（§6の実測でも週次利益見込み142万円という高リターン特性は
  維持されていることを確認済み）。到達週数はラーメンと同等かやや
  遅くて良い
- **コンビニ・不動産仲介**: §3の構造バグ修正後に実測してから、
  ラーメンとの相対ペース差を決める（現時点では未確定）

**業種を選ぶこと自体に意味が残ることが目的。** 機械的に同じ係数を
4業種に一律適用しないこと。

### 実装内容

ジム1号店専用の開業ローンを追加。適用条件は第13週まで・既存ジムなし・
通常融資後の不足額が550万円以内の場合に限定し、不足額に運転資金100万円を

開業ローンは会社現金・会社債務・既存の財務台帳・銀行融資履歴に記録される。
個人資金には触れず、信用スコアにも負担を持たせている。出店見積りと

最安テナント・決定論的LCG）を使い、4業種を開店後8週間まで実測する
回帰テストを追加。店舗原価・資金ショート・破綻・会計整合性・

# GitHub・PR・Codex開発運用仕様

## 1. 目的

本章は、資本主義ポケット TYCOON / Capitalism Tycoon Web のGitHub運用、Pull Request、Codex開発指示、レビュー、マージ、リリースまでの標準手順を定義する。AIと人間のどちらが作業しても、同じ品質基準で開発を継続できる状態を目的とする。

## 2. 正本

優先順位は以下とする。

1. `docs/` の承認済み仕様
2. `main` の実装とテスト
3. GitHub Issue・PRの決定事項
4. チャット上の補助説明

チャット上の指示が仕様と矛盾する場合、PR内で矛盾を明示し、仕様更新または実装修正を行う。未記録の口頭判断だけで恒久仕様を変更してはならない。

## 3. ブランチ

原則として`main`へ直接コミットしない。

命名例:

- `feat/<short-name>`
- `fix/<short-name>`
- `test/<short-name>`
- `docs/<short-name>`
- `refactor/<short-name>`
- `chore/<short-name>`

ブランチは単一の目的を持つ。無関係な機能、整形、依存更新を混在させない。

## 4. Issue

大規模機能、複数PRに分かれる作業、既知バグ、設計判断はIssueを作成する。

Issueには以下を含める。

- 背景
- 現象または目的
- 完了条件
- 影響範囲
- セーブ互換性
- 会計影響
- 決定論への影響
- iPhoneへの影響
- テスト方針

## 5. PRサイズ

PRはレビュー可能な単位に分割する。ただし、単一機能を不自然に分割して一時的に壊れた状態を`main`へ入れてはならない。

大規模変更では以下の順を推奨する。

1. データモデルと移行
2. 純粋ロジック
3. UI
4. 自動テスト
5. バランス調整

## 6. PR本文

PR本文には最低限以下を記載する。

- 概要
- 変更理由
- 主な変更
- 仕様書との対応
- セーブ互換性
- 会計・決定論への影響
- iPhone確認
- テスト結果
- 未解決事項
- スクリーンショットまたは動画（UI変更時）

## 7. コミット

コミットは意味のある単位にする。

推奨プレフィックス:

- `feat:`
- `fix:`
- `test:`
- `docs:`
- `refactor:`
- `chore:`

「update」「fix again」など内容不明なメッセージを避ける。

## 8. Codexへの指示

Codexへ渡す指示は以下を含める。

1. 対象リポジトリ
2. 最新`main`確認
3. 関連仕様書
4. 変更目的
5. 変更禁止事項
6. 完了条件
7. 必須テスト
8. PR作成要件

Codexは作業開始前に、対象コード、関連テスト、セーブ仕様を確認する。

## 9. Codex禁止事項

- `SAVE_KEY`を理由なく変更しない
- `saveVersion`を更新せずに破壊的変更しない
- `Math.random()`等の非管理乱数をゲームロジックに追加しない
- 会社資産と個人資産を直接相互移動しない
- テストを削除してCIを通さない
- エラーを握りつぶさない
- iPhone表示を未確認で完了扱いしない
- 仕様にない大規模リファクタリングを混在させない

## 10. レビュー基準

レビューでは以下を確認する。

### 10.1 正しさ

- 仕様どおりか
- 境界条件が処理されているか
- 二重計上がないか
- 不正な負数やNaNが生じないか

### 10.2 セーブ

- 旧セーブを読めるか
- 新規フィールドに既定値があるか
- 移行が冪等か
- 失敗時に元データを保護するか

### 10.3 決定論

- 同一seedで結果が一致するか
- UIやログで乱数を消費していないか
- 配列順序に依存する不安定処理がないか

### 10.4 会計

- 現金変動と仕訳が一致するか
- PL・BS・CFの整合性があるか
- 会社・個人・子会社の境界が守られているか

### 10.5 UI

- iPhone縦持ちで操作可能か
- タップ領域が十分か
- モーダルが画面外に出ないか
- 重要情報が省略されすぎていないか

### 10.6 テスト

- 新規ロジックの単体テスト
- 回帰テスト
- Playwright
- 長期シミュレーション

## 11. CI

PRでは原則として以下を実行する。

- lint
- typecheck
- unit tests
- deterministic regression
- accounting invariant tests
- save migration tests
- Playwright smoke tests
- build

失敗したテストを単にスキップしてはならない。フレークが疑われる場合は原因を記録し、再現条件を調査する。

## 12. マージ条件

以下を満たすまでマージしない。

- 必須CI成功
- 未解決レビュー指摘なし
- 仕様書更新済み
- セーブ影響確認済み
- iPhone確認済み
- 重大なTODOなし

推奨はsquash mergeとし、PR単位で履歴を追跡可能にする。

## 13. 緊急修正

重大な本番障害では小規模なhotfixを許可するが、以下を省略しない。

- 再現テスト
- 原因説明
- セーブ保護
- 修正後の回帰試験
- 後続Issue

## 14. リリース

リリース前に以下を確認する。

- ビルド可能
- 新規ゲーム開始
- 既存セーブ読込
- 週送り
- 店舗操作
- 借入・返済
- セーブ・再読込
- iPhone Safari
- 主要Playwrightシナリオ

## 15. ドキュメント更新

ゲーム仕様、データモデル、セーブ、処理順序、UI導線を変更するPRは、関連`docs/`を同じPRで更新する。

## 16. 完了条件

開発作業はコードを書いた時点では完了しない。仕様、実装、テスト、PR説明、iPhone確認、セーブ互換性確認が揃って完了とする。

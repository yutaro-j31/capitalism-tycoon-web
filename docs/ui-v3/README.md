## 2. 合格基準（数字で判定する）

すべての画面が、390×664・創業直後の状態で次を満たすこと。`node scripts/ui3-screen-metrics.js --ui=3 --enforce` が0で終われば合格。

| 基準 | 値 | 理由 |
| --- | --- | --- |
| 画面の長さ | 2画面分以内 | 詳細はシートへ逃がす。長い一覧も初期表示は2画面分まで |
| 最小の文字 | 13px | これより小さい文字は置かない。例外なし |
| タップできる部品 | 44×44px以上 | 主ボタンは48px |
| 横方向のはみ出し | なし | |
| ページエラー | 0件 | |

計測できないが必ず守ること：

- **1画面の主ボタンは1つ。** 金色（`--u-accent`）のボタンは1画面に1つだけ。
- **数字と単位を改行で分けない。** 金額には必ず `.u-money`（`white-space:nowrap`）。
- **金額の文字色は既定の白。** 増減だけ緑と赤（符号つき）。青と紫は財布を示す丸印（`.u-wallet` の点）とラベルに使い、数字は染めない。会社と個人の金額が同じ画面に並ぶとき、または使える現金を示すときは、丸印かラベルで財布を示す。どちらの財布か分からない金額を出さない。（2026-11-11 設計担当が確定）
- **増減の色は緑と赤だけで伝えない。** 必ず `+` `−` の符号を付ける。
- **確認が要る操作はシートで確認する。** ブラウザの `confirm()` を新しく使わない。お金が動いて取り消せない操作（契約、購入、売却、出資、借入）は、v3 では確認シートを挟む（金額と実行後の現金を表示し、既存の `action` を呼ぶ）。共通部品は UI3-4 で作り、UI3-6 とマップにも適用する。UI3-3（#1379）は現行どおりでよい。（2026-11-11 確定）
- **ホバーに頼らない。** 長押しにも頼らない。

下のタブは5つに固定する。現在の19画面（`g.selectedTab` の値）は消さず、5つのタブの中に並べ直す。`g.selectedTab` の値と意味は変えない。

| タブ | 入る画面（`selectedTab`） | 上部チップの並び |
| --- | --- | --- |
| ホーム | `home` `missions` `news` | なし（`missions` と `news` はホームから開くシート） |

- 画面の切り替えは、既存の `data-action="tab" data-tab="<id>"` をそのまま使う。

## 4. 部品

定義は `ui3.css`。新しい見た目が必要になったら、まずここにある部品で組めないか確かめる。組めないときは `ui3.css` とこの表に部品を足してから使う。画面ごとの独自の見た目を作らない。

| クラス | 使いどころ |
| --- | --- |
| `.u-card` | 数字のまとまり。1画面に2枚まで |
| `.u-stat`（`.hero` で大） | ラベル＋数字＋増減。横に並べるときは `.u-stats`（3列）か `.u-stats.two` |
| `.u-action`（`.warn` で注意） | 「今週やること」「次の一手」。カード全体が1つのボタン |
| `.u-list` と `.u-row` | 一覧。1行は左に名前と補足、右に数字と増減。行を押すと詳細シート |
| `.u-chips` と `.u-chip` | 画面の切り替え（`aria-current`）と絞り込み（`aria-pressed`）。横に流す |
| `.u-seg` | 2〜4択の切り替え（口座、業種など） |
| `.u-field`、`.u-input`、`.u-error` | 入力欄（ラベルと入力の組、入力、誤りの行）。金額・数量の入力シート（5.7）で使う |
| `.u-btn`（`.primary` `.wide`） | シート下端のボタン |
| `.u-badge`（`.good` `.warn`） | 状態を示す短い語 |
| `.u-pin`（`.tenant` `.store` `.realestate` `.rival`） | 地図の目印。見た目32px、当たり判定44px |

色と文字の値は `ui3.css` 冒頭の `--u-*` を使う。色コードや文字サイズを画面のCSSに直接書かない。

## 5. 画面ごとの仕様

### 5.1 ホーム（`home`）

上から順に、これだけを置く。これ以外は置かない。

1. 会社名と成長段階のバッジ
2. 数字のカード：**今週の利益**（大・前週比つき）、売上、企業価値、店舗数
3. **今週やること**：`.u-action` を最大3件。出どころは既存の Executive Secretary の優先順位と創業ガイドの現在の手順。危険（資金不足など）があれば `.warn` で先頭に出す
4. ニュース：最新2件。押すと全件のシート（`news`）

細部（2026-11-11 確定）：

- 成長段階のバッジは、`engine.growthMilestones()` のうち、並び順で最後に達成済みのものの名前。
- 「今週やること」の並びは、秘書の優先度が critical のもの（`.warn`）→ 創業ガイドの現在の手順 → 残りを秘書の優先順位の順。合わせて最大3件。
- ニュースの行は、UI3-9でシートに替わるまでは `news` 画面へ移動する（`data-action="tab"`）。
- 増減は `+` と `−`（U+2212）の符号を付け、金額は `compactYen` で整形する。
- 資金繰りが「安定」でない間、ホームは現行UIで出る（6.5）。危機対応の操作がそこにしか無いため。

実装で決めたこと（UI3-1、2026-11-11。設計担当の確認待ち）：

- 数字のカード：利益と売上は `ceoDashboard.weeklyImpact`（最新のレポート）、企業価値は `engine.companyValue()`、店舗数は営業中の店舗の数。前週のレポートが無いときは、利益の補足を「前週比較なし」とする。
- 利益は `+` `−` を付けて大きく出し、前週比も同じ規則（変化なしは「変化なし」、符号なし）。増えたら `u-up`、減ったら `u-down`。
- 今週やること：秘書の危険（critical）→ 創業ガイド → 残りの順。札の記号は、危険が「⚠」、創業ガイドが「📘」、ほかが「💡」。創業ガイドの札の表題は `創業ガイド N/10：手順名`、補足は手順の説明。何も無いときは「いま急ぐことはありません。」と1行だけ出す。
- 創業ガイドが要約・完了の表示のときは、現行のホームと同じく「成長ロードマップ」（`founding-tutorial-jump` → `missions`）の札を、創業ガイドの位置に出す。`missions` がホームのシート（UI3-9）になるまで、この入口を失わないため。
- ニュースの行は、文頭の `第N週：` を取って補足に移し、本文を表題にする。ニュースが1件も無いときは、見出しごと出さない。

現行ホームの「30秒で読む会社ホーム」などの読み物は置かない。必要な情報は「会社 › 決算」に移す。

### 5.2 マップ（`map`）

- **地図は現行の3D表示（`js/city-lab-map.js`）をそのまま主役にする。** 平面の地図に置き換えない。見本の地図は、実際のゲームの3D表示を写したもの。
- 地図は上のバーから下のタブまでの全面。現行（366×416）より広く取り、建物の高さと街並みが見えるようにする。
- ピンは建物の屋上の位置に立てる（現行の3D座標の投影をそのまま使う）。選択中の建物は、現行の選択枠を金色（`--u-accent`）にして強調する。
- ピンを選んでシートが出たら、その建物がシートに隠れない位置（地図の見えている部分の中央）に来るようカメラを寄せる。
- 地図の上に重ねるのは、絞り込みチップ1行と、右端の拡大・縮小・一覧の3ボタンだけ。現金や「今週の経営判断」の札は置かない（上のバーとホームにある）。
- 目印は種類ごとの丸いピン。**名前の札は選択中の1つにだけ出す。** ピン同士の衝突で隠さない（隠すのは画面外のときだけ）。
- ピンを押すと下からシートが出る（高さ58%まで）。地図は上に残す。
- 「一覧」ボタンで、同じ絞り込みの一覧シートを出す。
- 3D地図・Canvas2Dの予備表示・カメラの決まりは `CLAUDE.md` §4 のまま。変えるのは地図の上に載る部品とピンの見た目だけ。

### 5.3 出店シート（マップでテナントを選んだとき）

1. 見出し：テナント名、適性バッジ、補足1行（商圏・交通量・週額賃料）
2. 業種の切り替え `.u-seg`
3. 数字3つ：初期費用、週の利益見込み、回収までの週数
4. 補足1行：出店後の会社現金、開店までの週数
5. 下端：`試算の内訳`（内訳のシート）と **`出店する`**（主ボタン）

`出店する` は既存の最終確認（`confirmOpenStore`）につなぐ。既存の `open-store` は `#business-<テナントID>` の値を読むので、同じIDの入力を必ず用意する。

実装で決めたこと（UI3-3）：

- 地図の本体（`js/city-lab-map.js`）は、`pins:'u-pin'` を渡したときだけ v3 の表示になる（既定は従来どおり）。この表示では、ピンは `.u-pin`、衝突で隠さない（画面外だけ隠す）、選択枠は金色、選択中のピンだけ名前の札を出す。カメラの決まり（`CLAUDE.md` §4）は変えていない。`js/city-lab-map.js` を変えたので `node scripts/stamp-asset-revision.js` を実行した。
- ピンを選ぶと、そのピンが「シートに隠れない部分」の上寄り（地図の高さの27%の位置）に来るようカメラが寄る（`focusY`）。倍率は1.3。
- v3 のピンは、先端が地図の上端から100px以上下にあるものだけ表示する（画面外の扱い）。丸はピンの先端の上に最大44px伸びるので、チップの行（上端から12〜56px）の下に丸が潜り込まないためには、先端が56+44=100px以上要る（設計担当が承認、2026-11-11。最初の指示の72pxは丸の分の見落としだった）。
- 地図の上に重ねるのは、チップ1行（左端が都道府県、続いて すべて／自社店舗／出店候補／オフィス／不動産／競合）と、右端の ＋ − 一覧。都道府県の切り替えは、現行地図の `select`（`data-bind="selectedPref"`）をチップ行の先頭に移して使う（既存の操作。テナントが都道府県ごとにあるため、仕様に無いが外せない）。「全体」「表示」ボタン、今週の経営判断の札、現金、画面下の「1週間進める」は置かない。
- シートの高さは58%まで。シートが開いている間も地図は上に見える。**地図の見えている部分をタップするとシートが閉じる**（出店シートの下端のボタンは仕様どおり2つだけで、閉じるボタンを置かないため）。ピンやリストの行をタップした直後（450ms以内）の、タッチが後から送る `click` は無視する。
- 出店候補以外のピンのシートは、仕様に無いので、現行の詳細パネルと同じ事実と操作を出す（自社店舗：売上・利益→事業へ／オフィス：賃料・保証金→契約（本社を設置済みなら支社として契約）／不動産：価格・賃料→会社・個人で購入、価格交渉（保有中は売却）／競合：店舗数・価格→競合へ）。
- 業種の切り替えは、シートの中だけの表示状態（`g.selectedBusiness` は書かない）。初期値は、`g.selectedBusiness` が出店できる業種ならそれ、なければ先頭（ラーメン）。
- `.u-seg` のボタンの44pxは `ui3.css` 側で直した（設計担当の決定 2026-11-11）。地図のシートの個別の上書きは無い。
- 3D地図が使えないとき（WebGL・アセット・コンテキストの失敗）は、6.5の扱いでその間だけ地図を現行UI（Canvas2Dの予備表示）で出す。

### 5.4 週間レポート

1画面のシートに収める。スクロールさせない。

1. 見出し：`第N週の結果` と、結果を一言で表す文（黒字／赤字／現金が減った、など）
2. 数字：**利益**（大）、売上、会社現金。それぞれ前週比つき
3. 今週の出来事：最大2件
4. 次の一手：`.u-action` 1件
5. 下端：`詳しい決算`（`report` へ）と **`閉じる`**（主ボタン）

現行レポートの「利益と現金の差」の内訳などは「会社 › 決算」に置く。

実装で決めたこと（UI3-2、2026-11-11。設計担当の確認待ち）：

- 週間レポートは画面ではなくシートとして登録する（`registerSheet('weekly-report', {render})`。6.1）。`?ui=3` のとき、`js/app.js` の `showWeeklySummary()` が先に `modules.ui3.renderSheet('weekly-report', …)` を呼び、答えがあればそれを `#modal-root` に入れる。週を進める2か所（1週間・4週間）のどちらも同じ関数を通る。
- 見出しは、上に `第N週の結果`、その下に一言文。一言文は、利益が黒字のとき「黒字が続いています」（前週も黒字）／「黒字でした」／現金が減ったとき「黒字でしたが、現金は減りました」、赤字のとき「赤字が続いています」（前週も赤字）／「赤字でした」／現金が減ったとき「赤字で、現金も減りました」、ゼロのとき「収支はゼロでした」／現金が減ったとき「利益は出ず、現金は減りました」。現金の増減は、現行のレポートの「利益と現金の差」と同じ `finance.cashBridge(g, 'week')` の「今週の現金増減」。
- 数字は、利益（大）・売上・会社現金。値と前週比は `ceoDashboard.weeklyImpact`。符号と色の規則はホームと同じ（5.1）。
- 今週の出来事は、その週のニュース（`g.news` のうち `第N週：` の N が `summary.week` と一致するもの）の先頭2件。文頭の `第N週：` は取る。`summary.newNews` は使わない（前回のレポート以降に増えたものなので、古い週を含みうる）。1件も無いときは「大きな出来事はありませんでした。」とだけ出す。（2026-11-11 設計担当が確定）
- 次の一手は、秘書の危険（critical）なタスク（`.warn`）→ 創業ガイドの現在の手順 → 秘書の先頭のタスク → 「ホームを見る」の順で1件。押すと、`secretary-jump` や `founding-tutorial-jump` ではなく **`tab`** でその画面へ移る（この2つはモーダルを閉じないため）。
- 下端は `詳しい決算`（`tab` → `report`）と `閉じる`（`close-modal`。主ボタン）。
- 1画面（スクロールなし）に収めるため、`css/ui3-weekly-report.css` で、シートの中の隙間・カードの内側の余白・出来事の行の最小の高さを詰め、出来事の見出しと次の一手の見出しを2行まで、補足を1行までにしている（色と文字の大きさは触っていない）。
- このシートは、現行UIが出している画面（まだ移していない画面）の上にも出る。重なり順は `ui3.css` の `.u-scrim` `.u-sheet`（100/101、現行のモーダルと同じ）がそのまま効くので、この週間レポート専用の上書きは無い（設計担当の決定 2026-11-11）。また、現行UIのCSSが `#modal-root` の中の `h2` `p` `small` の色を強制するため、見出しは `h2` ではなく `role="heading"` の `div` にし、次の一手の補足の色だけ上書きしている。

### 5.5 そのほかの画面の型

残りの画面は、次の3つの型のどれかで作る。各画面で決めるのは表の4項目だけ。

- **ハブ型**：見出し → チップ → 数字のカード1枚 → 一覧。例は見本の「投資」
- **一覧型**：絞り込みチップ → `.u-list`。行を押すと詳細シート
- **詳細シート**：数字3つ → 補足 → 下端に主ボタン1つ

実装で決めたこと（UI3-4：`business` `office`）：

- `business`：カードは「店舗（運営中と準備中の数）・週の利益（営業中の店舗の `lastProfit` の合計）・最も稼ぐ店」。一覧は、店舗（行 → 店舗のシート：コンセプト変更・設備強化・改装・店舗価格・閉店）、運営中の事業（行 → 事業のシート：投資4種・価格変更・FC本部の設置・加盟店募集）、未出店の業種（現行と同じく地図へ）。続けて「IT・デジタル事業」（シート）と「ほかの詳細（現行の画面）」の行。
- `office`：カードは「本社（名前）・社員数・週の固定費」。一覧は設置済みの部門と在籍のCXO（読み取りのみ）、「操作」（福利厚生投資・リモートワーク・本社契約の解除）、「ほかの詳細（現行の画面）」。
- **お金が動いて取り消せない操作は共通の確認シート `modules.ui3.confirmSheet` を通す**（6.1）。この画面で通すのは、コンセプト変更・設備強化・改装・FC本部の設置。金額の入力が要る操作（事業投資・価格変更・店舗価格・福利厚生投資・加盟店募集）と、結果を事前提示する現行のダイアログがある操作（閉店・本社契約の解除）は、その現行のダイアログがそのまま確認になる（金額入力のv3のシートは新しい部品になるため作っていない。未決事項）。
- v3 に載せない操作は、「ほかの詳細（現行の画面）」の行（`data-ui3-current`、6.5）から現行UIの画面を開いて届く。押すとその画面だけ現行UIになり、**次の `tab` 操作で v3 に戻る**。仕組みは枠の `openCurrentUI` にあり、画面側に個別の実装は無い。
- 事業 × リコール危機が未対応の間は、枠の規則（`CURRENT_UI_RULES.business`）で事業画面を現行UIで出す（6.5）。
- トースト：v3 のシートが出ている間だけ、画面の上端に出す（`ui3.css`）。シートの下端の確認の金額を隠さないため。
- FC本部の費用の写し（`FRANCHISE_HQ_COST`）は、検査が `js/engine.js` の `startFranchise` の金額と一致することを確かめる（ずれたら CI で落ちる）。
- 金額入力は UI3-9a（5.7）のシートになった。
- `.u-chip` のボタンは `ui3.css` で40pxだったが、合格基準は44px以上なので、`ui3.css` と `docs/ui-v3/ui3.css` を同時に44pxにした（`.u-seg` と同じ扱い。地図の個別の上書きは消した）。
- 店舗のシートの行は `.u-row` を使う（`ui3.css` の既存の部品）。行を押せない状態（資金不足・条件未達）は `disabled`。

実装で決めたこと（UI3-5：`market`）：

- カードは「（個人／会社の）現金・保有の時価・含み損益」。現金のラベルに財布（「個人の現金」「会社の現金」）を付ける（2章）。保有の時価は `数量 × 株価` の合計、含み損益は `(株価 − 平均取得価格) × 数量` の合計。
- 画面の上に投資口座の切り替え（`.u-seg`：個人口座／会社口座）。口座は画面の表示状態で、`buy-stock` `sell-stock` が読む現行UIの設定（`data-bind="selectedAccount"`）は、隠した `select` の `change` で合わせる。売買ボタンを押す前にも合わせるので、現行の画面で口座を変えたあとでも食い違わない。
- 一覧は「保有・お気に入り」の行（銘柄のシートへ）と、「銘柄を探す」（全銘柄のシート。業種チップで絞り込み）。全36銘柄を初期表示に並べない（2画面分に収めるため）。
- 銘柄のシート：株価・前週比・保有、平均取得価格、お気に入りの切り替え、下端に「売る」「買う」（主ボタン）。**売買は株数の入力が要るので、確認シートは通さず、UI3-9a の金額入力シート（5.7）が確認になる**（株数を入れると、概算の金額と実行後の現金が出る）。会社口座の売買は、ゲーム側の規則（投資部門が必要）で拒否されることがある。その表示も現行のとおり。
- 会社口座を選んでいて投資部門が無いときは、画面の `.u-seg` の下に警告の札（`.u-action.warn`「会社口座の売買には投資部門が必要です」。押すと本社画面へ）を出し、銘柄シートの「買う」「売る」を `disabled` にして同じ理由を補足に出す。条件は現行の株式購入パネル（`js/app.js` の `stockTradeCapacity`）と同じ（`departments.investment` を読むだけ）。
- 自社株の操作・チャート・信用取引・資本配分は、「ほかの詳細（現行の画面）」の行（`data-ui3-current="market"`、6.5）から届く。

### 5.7 金額入力シート（UI3-9a）

現行の金額・数量の入力ダイアログ（`js/app.js` の `askMoney`。iPhone 用は `js/iphone-playtest-fixes.js`）を、v3 のシートにする。株の売買の入力は、題が「購入株数」なのに欄のラベルが「金額（円）」で、合計も実行後の現金も出ないため、最初に直す（設計担当の決定 2026-11-11）。

1. **差し込み**：`js/app.js` の `askMoney` の先頭に1行だけ足す。v3 が有効なら `modules.ui3.amountSheet({title,initial,submit})` に任せ、真が返ったら `return`。v3 が無効なら従来どおり。`js/iphone-playtest-fixes.js` の入力ダイアログとの関係を確かめ、v3 が有効なときはどちらも出ないようにする。
2. **枠**：`modules.ui3.amountSheet({title,initial,submit})` を `js/ui3-shell.js` に足す。`#modal-root` にシートを出す。
   - 見出し：`title`。
   - 入力欄：ラベルは単位（「株数」または「金額（円）」）。`inputmode="numeric"`、高さ48px、文字20px。初期値は `initial`。
   - 候補のチップ：株数は 100／500／1,000、金額は 10万／50万／100万。上限が分かるときは「最大」を足す。
   - 見込みの行：下の「文脈」があるときだけ、概算の金額と実行後の現金（どちらの財布かを明記）を出す。入力のたびに更新する。実行後の現金が負になるときは赤で出す（実行は止めない。可否はエンジンが決める）。
   - 誤りの行：入力が正の整数でないとき、理由を出して「実行する」を `disabled` にする。現行の `askMoney` が受け付ける値の範囲を確かめ、同じにする。
   - 下端：「やめる」（`close-modal`）と「実行する」（主ボタン）。実行で `submit(value)` を呼び、シートを閉じる。Enter でも実行。
3. **文脈**：`modules.ui3.setAmountContext({unit:'株'|'円',unitPrice,wallet:'company'|'personal',direction:'spend'|'receive',max,note})` を足す。画面側が `action` を出す直前に呼び、次の `amountSheet` が1回だけ使って消す。文脈が無いときは、`title` に「株数」を含めば株、それ以外は円として、見込みの行は出さない。market の「買う」「売る」は文脈を渡す（株価、口座、買いは `spend`・売りは `receive`、買いの上限）。business と office の金額入力（事業投資・価格変更・店舗価格・福利厚生投資・加盟店募集）も、このシートになる。文脈は渡せる範囲で渡す。
4. **部品**：`ui3.css`（`docs/ui-v3/ui3.css` と同時）に `.u-field`（ラベルと入力の組）、`.u-input`、`.u-error` を足す。値は既存の `--u-*` だけを使う。4章の表にも載せた。
5. **検査**：`tests/ui3-amount-webkit-test.js`。`?ui=3` なしでは現行のダイアログのまま。`?ui=3` でシートが出る。「やめる」は何も変えない。株を10株買うと、見込みの金額が 株価×10、実行後の現金が表示どおりになる。正の整数でない入力では実行できない。最小の文字13px、タップ44px、横はみ出しなし。既存の ui3 の検査で現行ダイアログを前提にしている確認は、v3 のシートを前提に書き直してよい（設計担当の承認済み。確認の中身は弱めない）。
6. **台帳**：UI3-9a の対象として載せた行を「v3 の金額入力シート」に更新する。

実装で決めたこと（UI3-9a）：

- 単位は文脈の `unit`（`'株'` `'円'` `'店'`）。文脈が無いときは `title` で決める（「株数」を含む→株、「募集数」を含む→店、それ以外→円）。「店」は加盟店募集の件数のために足した（承認済み。ラベルは「店数」、候補は 1・3・5）。
- 円の候補チップ（10万／50万／100万）は、`initial` が 10万円以上のときだけ出す（価格変更・メニュー価格・店舗価格・配当などで桁の合わない候補を出さないため）。文脈の `presets`（`[{value,label}]`）があれば、それを優先する（どの単位でも）。
- 文脈の `preview`（`(value) => [{label,value,tone?}]`）を渡すと、既定の見込みの行の代わりに使う。画面側が読み取りだけで組み立てる（利用可能枠、返済後残高など）。枠は表示するだけ。UI3-7 の借入・返済で使う。
- 文脈は、画面が `action` を出す直前に `setAmountContext` で渡し、次の `amountSheet` が1回だけ使って消す。使われなかった文脈が無関係なダイアログに届かないよう、3秒で失効する。
- 受け付ける値（設計担当の決定 2026-11-11）：円は **0 以上の数値（小数可）**、株・店は **1 以上の整数**（カンマは取り除く）。円で弾くのは負の値と数値でないものだけ（`engine.setDividend` は 0 と小数を受け付けるため、配当を 0 円にできる）。エンジンが使えない値（投資額 0 など）はエンジンが拒否する。空・規則に合わない値は「実行する」を `disabled` にして理由を出す。円は `inputmode="decimal"`、株・店は `numeric`。`askMoney` の29か所の単位と、0・小数が意味を持つかは台帳に1行ずつ載せた。
- 見込みの行は、文脈に財布があるときだけ。概算の金額は `値 × unitPrice`（`unitPrice` が無ければ値そのもの）。株の購入の上限は、現行の株式購入パネルと同じ規則（現金 ÷ (株価 × 1.001) を切り捨て）、売却の上限は保有数。
- 渡している文脈：株の売買（market）、事業投資・加盟店募集（business、会社の現金）、福利厚生投資（office、会社の現金）。価格変更・店舗価格は財布が無いので見込みの行なし。未移植の画面（銀行・ベンチャーなど）の入力も、文脈なしで v3 のシートになる（単位は円）。
- `js/iphone-playtest-fixes.js` の入力ダイアログは、`?ui=3` のときは出さない（その `action` は `js/app.js` の `askMoney` に流れ、v3 のシートになる）。`?ui=3` なしでは従来どおり。
- 名前の入力（`askText`）は対象外で、現行のダイアログのまま（UI3-9b に含める）。

UI3-6 以降の扱い（設計担当の決定 2026-11-11）：金額・数量の入力が要る操作は、UI3-9a のシートを通す（それまでは現行のダイアログのまま台帳に載せる）。入力が不要で金額が確定している操作（物件の購入・売却、出資、買収の実行など）は、確認シート（6.1）を通す。

## 6. 実装の決まり

### 6.1 切り替え方（UI3-0で実装済み）

- v3は現行UIと並んで動く。`?ui=3` を付けて開くとv3が有効になり、その端末の `localStorage['capitalism_tycoon_ui']` に記憶される。`?ui=2` で解除。**この設定はセーブデータに入れない。**
- 画面は1つずつ移す。`modules.ui3.registerScreen(<selectedTabの値>, {render})` で登録した画面だけがv3で描かれる。**登録していない画面は、現行UI（D UI）が外枠ごとそのまま出る。** 創業画面とゲームオーバーは、それぞれの作業で移すまで現行UIのまま。
- 入口は `js/app.js` の `render()`。`modules.ui3.rendersNatively(tab, g)` が真なら `modules.ui3.renderApp(...)` の結果を `#app` に入れる。偽なら `leaveNative()` を呼んで従来どおり描く。
- v3の画面にはD UIの後処理をかけない。`js/ui-enhancer-registry.js` の `runUIEnhancers()` は、v3の画面が出ている間（`modules.ui3.isNativeActive()`）は何もしない。現行UIに戻ると再開する。
- v3が描く最上位の要素に `class="ui3"` が付く。`ui3.css` は `.ui3` の内側（と、v3の画面が出ている間だけ付く `body.ui3-native`）にしか効かない。
- 全画面への到達は `[data-action="tab"][data-tab="<id>"]` で保証する。v3の枠は、画面に出ていないチップの分も含めて、隠した一覧（`[data-ui3-all-screens]`）に全画面のボタンを持つ。

画面の登録のしかた（`js/ui3-<画面>.js`）：

```js
(function(){'use strict';
const modules=globalThis.__capitalismTycoonModules;
modules.ui3.registerScreen('home',{
  // 返すのは <main id="screen"> の中身だけ。上のバー・進めるボタン・タブは枠が描く。
  // 事業・投資・会社の各画面では、見出し（タブ名）とチップも枠が描くので、画面側では見出しを出さない。
  render({engine,g,engineModule,esc,money}){
    return `<h1 class="u-h1">${esc(g.companyName)}</h1>`;
  }
});
})();
```

- `render` は文字列を返すだけ。`g` を読むのはよいが、書き換えない。利用者由来の文字列は必ず `esc()` を通す。金額は `money()`（`compactYen`）で整形する。
- シートは `modules.ui3.sheet({eyebrow,title,subtitle,body,actions})` の結果を `#modal-root` に入れる。閉じるのは既存の `data-action="close-modal"`。シートが出ている間、進めるボタンは自動で隠れる。
- 画面に、マークアップでは渡せないもの（3D地図の canvas など）を付ける必要があるときは、`registerScreen` に `mount(context)` を渡す。`js/app.js` が `#app` にマークアップを入れた直後（同じタスクの終わり）に、1回だけ呼ばれる。`context` は `{engine,g,engineModule,esc,money,host}`（`host` は `.u-app` 要素）。画面がまだ出ているときだけ呼ばれ、関数でなければ登録時に `TypeError`。
- 画面ではなく、`js/app.js` が出す現行のモーダルを置き換えるシートは、`modules.ui3.registerSheet(id, {render})` で登録する（`id` は `modules.ui3.SHEET_IDS` のもの。今は `weekly-report` だけ）。`render(context)` は `{eyebrow,title,subtitle,body,actions}` を返し、枠が `sheet()` で包む。`context` は `{engine,engineModule,g,esc,money}` と、呼び出し側が渡す値（週間レポートでは `summary`）。`js/app.js` は `modules.ui3.renderSheet(id, context)` を先に呼び、答えが空文字（`?ui=3` でない、未登録、未設定のゲーム）のときだけ、現行のモーダルを出す。
- お金が動いて取り消せない操作は、`modules.ui3.confirmSheet({eyebrow,title,subtitle,facts,note,confirm,cancelLabel})` の結果を `#modal-root` に入れて確認する。`facts` は `[{label,value,tone?}]`（整形済みの文字列。費用と実行後の会社現金を必ず入れる）、`confirm` は `{label,attributes}`（`attributes` は既存の `data-action` と `data-id` `data-kind`）。下端は「やめる」（`close-modal`）と主ボタン1つ。主ボタンを押すと js/app.js が既存の `action` を実行し、そのあとシートが閉じる（別のダイアログを開く `action` には使わない。そのダイアログごと閉じるため）。この部品は何も実行しない。
- スクリプトは `index.html` で `js/ui3-shell.js` の後、`js/app.js` の前に読み込む。

**現行UIの機能は、`js/app.js` が描くHTMLだけではない。** 約80個の enhancer が、描画後に画面へ機能を差し込んでいる（不動産の管理、危機対応、資本配分のメモなど）。v3の画面ではこれらが動かないので、画面を移すときは、その画面に差し込まれている機能も対応表（5.5）に載せ、v3側で出し直す。

新しいJSを足したら、同じPRで `index.html` と `tests/fixtures/module-load-order.json` を更新する。新しいCSSは `index.html` の `css/ui3.css` の後に足す。

新しい `js/ui3-*.js` が `companyCash` や `personalCash` などのお金の項目を読むと、経済エンジンの「書き込み箇所の一覧」の検査（`AUTHORITATIVE_WRITER_INVENTORY`）が、語が出てくるだけで候補として検出する。同じPRで `node scripts/phase0-5-acceptance.js --refresh-writers` を実行し、`docs/economic-engine/phase0-5-authoritative-writers.json` の差分が**自分のファイルの追加だけ**であることを確かめてコミットする。`exactAuthority` 側（実際の書き込み）に差分が出たら、それは状態を書き換えているということなので、コードを直す。

枠の検査（`tests/ui3-shell-webkit-test.js`）は、画面のスクリプト（`js/ui3-shell.js` 以外の `js/ui3-*.js`）を読み込まない状態でページを開き、検査用の仮の画面だけを登録して確かめる。**画面を移しても、この検査は変えなくてよい。** 画面ごとの検査は `tests/ui3-<画面>-webkit-test.js` に書き、そちらは実際のスクリプトを読み込んだ状態で確かめる。

検査の置き場所：v3の検査は `tests/ui3-*-webkit-test.js` とし、`tests/test-execution-registry.json` に登録して、`.github/workflows/test.yml` の「iPhone Acceptance Playthrough」ジョブに手順を足す。`tests/run-all.js` には足さない（登録数がシャードの保存済み証跡で固定されているため）。手元では `UI3_TEST_BROWSER=chromium UI3_TEST_CHROME=<Chromeのパス>` で実行できる。

### 6.3 してはいけないこと

- **エンジンの状態を直接書き換えない。** 操作は必ず既存の `data-action`（`js/app.js` の `action()`）を通す。新しい操作が要るなら、エンジン側の既存の関数を呼ぶ `action` を足す。
- 描画の中で乱数を使わない。`Math.random()` を使わない。
- 起動時の MutationObserver と、外部 enhancer の登録を増やさない（上限79）。
- `css/app.css` を変えない（バイト一致の検査がある）。
- 既存のテストを消さない・外さない・緩めない。現行UIのテストは、切り替えが終わるまで現行UIに対して通り続けること。

### 6.4 文言

- 画面の文言は日本語。英語の見出し（CEO DASHBOARD など）を置かない。
- 金額は既存の `compactYen` などの整形関数を使う。独自に整形しない。
- 1つの `.u-row` の補足は1行まで。説明文を置きたくなったら、その画面に置く情報が多すぎる。

### 6.5 現行UIに任せる状態（届き先が決まっていない操作の既定の扱い）

現行の画面には、特定の状態のときだけ出る操作がある（例：資金繰り危機のときの回復策）。その操作のv3での届き先がこの文書に無いときは、**止まらずに、その状態の間だけその画面を現行UIで出す。** 操作は1つも失われず、v3側の作り込みは後の作業に回せる。

- 画面の登録に `useCurrentUI(g)` を足す。真を返す間、その画面は現行UIが外枠ごと出る。偽に戻ればv3に戻る。

  ```js
  modules.ui3.registerScreen('bank',{
    useCurrentUI:g=>Boolean(g.someState),   // 読むだけ。g を書き換えない
    render(context){ /* ... */ }
  });
  ```

- 条件は、できるだけ狭く書く（「その操作が出る状態」だけ）。常に真を返す登録はしない。
**利用者が選んで現行の画面を開く行**：v3 の画面に載せない操作が残る画面では、行（ボタン）に `data-ui3-current="<screen>"` を付ける。押すと、枠が `modules.ui3.openCurrentUI(screenID)` を呼び、その画面だけ現行UIで出る。**次の `tab` 操作で v3 に戻る。** 状態で自動的に切り替える `useCurrentUI` とは別の仕組みで、画面側に個別の実装は持たない。使ったら、台帳の残件に画面ごとに1行ずつ載せる（UI3-11 の時点で0件）。

- 使ったら、必ず `migration-ledger.md` のその画面の表に、状態・現行UIで出る操作・残件を書く。
- 残った分は UI3-9b でv3に作り直す。**UI3-11（切り替え）の時点で、`useCurrentUI` と枠の規則は1つも残っていないこと。**

枠が最初から持っている規則（`js/ui3-shell.js` の `CURRENT_UI_RULES`）：

- **事業 × リコール危機が未対応**（`activeRecallCrisis` が有効で、`responded` が偽）：現行の事業画面だけが「自主回収・補償」（`respond-recall-crisis`）を出すため。`modules.companyRecallCrisis.view()` は状態を整える（書き込む）ので使わず、状態を読むだけで判定する。（2026-11-11 設計担当が確定）
- **ホーム × 資金繰りが「安定」以外**：現行ホームに差し込まれる危機対応のパネル（`js/player-crisis-ui.js`）が、回復策の唯一の入口のため。この間、v3のほかの画面には枠が「資金繰り危機」などの札を出し、押すとホーム（現行UI）へ移る。

### 各作業の進め方

**着手したら最初にやること**

1. 対象の画面を仮に登録した状態で、既存の `tests/ui3-*-webkit-test.js` を実行し、落ちるものが無いか確かめる。落ちたら、実装に入る前に報告する。
2. 現行の画面を実際に開き、出ている操作（`data-action`）を洗い出して、`migration-ledger.md` にその画面の表を作る。創業直後だけでなく、台帳の「確かめる状態」に挙げた状態でも洗い出す。enhancer が差し込む操作も含める。
   洗い出しには `node scripts/ui3-dump-screen-actions.js --screen=<画面> [--states=founding,store-open,crisis,office,listed] [--ui=2|3]` が使える（`data-*action*` の属性を持つ部品を、状態ごとに表で出す。`UI_METRICS_BROWSER=chromium UI_METRICS_CHROME=<Chromeのパス>` でChromiumでも動く）。`crisis` と `listed` は確認専用に状態を書き換えて見せるだけで、実際のIPOや危機ではない。作れなかった状態は「未確認」と出る。
3. 表のすべての行に、v3での届き先を書く。届き先が決まらない行は、6.5の扱い（その状態の間だけ現行UI）にして、残件として書く。

**PRに必ず入れること**

1. `node scripts/ui3-screen-metrics.js --ui=3 --enforce --screens=<対象>` の出力。
2. 390×664の画面写真（初期表示と、主な操作のシート）。
3. `migration-ledger.md` のその画面の表（届かなくなる操作が0であること）。
4. `?ui=3` なしで現行UIが変わっていないことを、既存の検査で示した結果。
5. この文書に書かれていない判断をしたら、同じPRでこの文書に書き足し、PR本文の「自分で決めたこと」に並べる。
6. 決められなかった点があれば、PR本文の「未決事項」に、選択肢と推奨を添えて書く。

### 担当が自分で決めてよいこと・止まること

**決めてよい（この文書に書き足して先へ進む）**

- エンジンや既存の画面にすでにある概念・値・文言から選ぶだけの判断（例：バッジにどの既存の値を使うか）
- 並び順、文言の言い回し、既存の部品の組み合わせ方
- 届き先が決まらない操作を、6.5の扱いにすること
- `js/app.js` への差し込みは、1か所1行で、v3 が無効なら従来どおりの動きになるものに限り決めてよい（PR本文の「枠の変更」に書く）。
- `js/ui3-shell.js` への小さな追加。条件は、既存の動きを変えない追加であること、`tests/ui3-shell-webkit-test.js` に確認を足すこと、PR本文の「枠の変更」に書くこと。枠の既存の動きを変える必要があるときは、止まる

**止まる（設計担当に戻す）**

- 新しいゲームの概念や数値を作る必要がある
- `ui3.css` に無い新しい部品、または新しい操作（`action`）が要る
- お金や状態を書き換える処理に触れる必要がある
- 既存のテストを変えないと通せない
- 6章の決まりを守ったままでは実装できない
- UI3-9b と UI3-11

止まるときも、手を止めるのは**その点だけ**。それ以外を実装し、未決事項つきの下書きPRを出してから報告する。設計担当の答えは、同じPRへの追加コミットで取り込む。

### どのモデルに任せられるか

設計上の判断はこの文書で済ませてあるので、UI3-1以降は軽いモデルで進められる。上位モデルが要るのは次の場面だけ（依頼文と戻し方は9章）。

- **UI3-0**：現行の描画・後処理との切り分けを決める作業。
- **UI3-11**：既存テストの置き換え計画。
- **UI3-9b**：仕様を書く作業（実装は軽いモデルで可）。
- 各PRの内容確認と、上の「止まる」に当たる判断。

# 仕様書整合性・現行コードギャップ監査

## 1. 目的

本章は、`docs/01`〜`docs/30`で定義した正本仕様と、`main`ブランチの現行実装との主要な差分を記録する。

本監査は、仕様の完成を宣言するものではない。実装着手前に解消すべき矛盾、技術的負債、未実装の品質ゲートを優先順位付きで示す。

## 2. 監査範囲

確認対象:

- `package.json`のテスト・リリーススクリプト
- `index.html`のモジュール読込構造
- `js/runtime.js`
- `js/engine.js`
- `js/save-v9.js`
- 既存テスト名から確認できる会計、市場、供給、人材、競合、M&A、危機対応、長期試験のカバレッジ
- `docs/01`〜`docs/30`の最上位原則と相互参照

本章に記載していない機能が適合済みであることを意味しない。各マイルストーン開始時に対象コードを追加監査する。

## 3. 総合判定

現行コードは、単純な試作段階を超え、以下の領域に相当量の回帰試験を持つ。

- セーブ互換・移行
- 会計仕訳・財務諸表・キャッシュフロー
- 市場、供給、在庫、調達
- 人材、給与、疲労、離職、部門
- 競合AI、参入退出、信用、倒産
- M&A、取得資金、取締役会承認
- プレイヤー企業の危機・再建
- 長期実行とバランス監査

一方、マスター仕様の最上位原則に対して、次のP0/P1ギャップが残る。

1. 管理乱数へ統一されておらず、初期生成に`Math.random()`と時刻依存IDが残る
2. 安定ID方針と、ランタイム生成UUIDの使用が一致していない
3. セーブバージョンの正本が`engine.js`のv8と`save-v9.js`のv9に分散している
4. 古典的script読込と後付けパッチが多く、ロード順への結合が強い
5. Playwrightによる実ブラウザ・iPhone相当E2Eがリリーススクリプト上で確認できない
6. JSON Schemaが仕様として定義されているが、機械検証可能なスキーマファイルが未整備

## 5. 現行コード適合状況

### 5.1 適合度が高い領域

#### 会計と資金移動

`package.json`には、仕訳、財務諸表、キャッシュフロー、運転資本、会計不変条件、ユーザー操作スナップショット、現金変更網羅、M&A会計、不動産売却などの専用試験が定義されている。

判定: **概ね適合。継続監査対象**

残課題:

- すべての現金変更経路がfinanceモジュールを通ることの静的保証
- 新規機能追加時の会計イベント登録漏れ防止
- 会社資産・個人資産間振替の専用不変条件強化

#### 市場・供給・人材・競合

市場の順序不変性、乱数回帰、共食い、供給、在庫ロット、廃棄、人材の週次一回処理、競合の参入退出・信用・倒産など、仕様に対応する試験群が存在する。

判定: **主要基盤は実装済み**

残課題:

- すべての乱数が同一seedから再現可能かの横断監査
- モジュール間の処理順を1か所で宣言する仕組み
- 長期試験結果の標準レポート化

#### セーブ移行

v0相当の旧データからの移行、v9移行、読込統合試験が存在する。将来版拒否、読込失敗時の保存ブロックもコード上で考慮されている。

判定: **機能は存在するが構造上の整理が必要**

## 6. 重大ギャップ

### GAP-P0-01 管理乱数への未統一

現状:

- `engine.js`に`Math.random()`を直接使う`rand`、`pick`がある
- UUIDのフォールバックが`Date.now()`と`Math.random()`へ依存する
- 初期役員の年齢・性別などが直接乱数で決まる

仕様との衝突:

- 同一seed・同一入力・同一処理順で同一結果になるという決定論要件
- 自動プレイ結果の再現性

必要対応:

1. `RandomService`または同等の管理乱数器を唯一の乱数入口とする
2. stateへseedと乱数位置を保存する
3. ID採番はseed依存または単調連番へ変更する
4. `Math.random`直接呼出しをCI静的検査で禁止する
5. 既存セーブのIDを壊さない移行を用意する

### GAP-P0-02 セーブバージョン正本の分散

現状:

- `engine.js`は`SAVE_VERSION = 8`
- 後から読み込む`save-v9.js`がengine exportsをv9へ置換する
- 初期stateは基底生成後にv9へスタンプされる

リスク:

- script読込漏れや順序変更でv8へ退行する
- テストが基底engineだけを読み込んだ場合に実運用と異なる
- 新しいv10以降でラッパー階層が増える

必要対応:

1. 現行バージョン定数を単一ファイルへ集約する
2. `migrations/8-to-9`のような明示的移行チェーンへ変更する
3. 初期state生成時点で現行版を付与する
4. アプリ起動時に登録済み移行の連続性を検査する
5. `SAVE_KEY`は変更せず互換性を維持する

### GAP-P0-03 安定IDとランダムUUIDの不一致

現状:

- 物件、スタートアップ、役員、競合などにランタイムUUIDを付与している
- 一部テナントやオフィスには`stableKey`があるが全データへ統一されていない

リスク:

- 同一seedでも参照IDが変わる
- マスター更新時にセーブ参照が切れる
- 差分比較と回帰テストが不安定になる

必要対応:

- マスターデータ由来IDは固定文字列ID
- プレイ中生成エンティティは種類別連番
- 表示名を参照キーにしない
- 旧UUIDを保持しつつstable IDを追加する段階移行

### GAP-P0-04 ブラウザE2E・iPhone相当試験の未統合

現状:

- Nodeベースの回帰試験は多数存在する
- `package.json`上ではPlaywrightの実行スクリプト、依存関係、WebKit/iPhoneプロジェクトを確認できない

仕様との衝突:

- ブラウザ版・iPhone最優先
- 主要導線をPlaywrightで自動プレイする方針

必要対応:

1. Playwrightを導入する
2. iPhone縦持ち相当のWebKitプロジェクトを追加する
3. 創業、出店、週送り、保存、再読込、倒産・再建のsmokeを実装する
4. console error、page error、無限ローディングを失敗条件にする
5. PR用短時間E2Eとnightly長期E2Eを分離する

## 7. P1ギャップ

### GAP-P1-01 scriptロード順と後付けパッチの複雑化

`index.html`は多数のclassic scriptとinline bridgeを順番に読み込む。各ファイルがglobal registryを拡張し、後続ファイルが前提モジュールを検査する構成である。

リスク:

- 読込順変更による起動不能
- 同じprototypeを複数拡張する競合
- 起動時の責務と機能実装の混在
- iPhone Safariでの初期ロード性能悪化

対応方針:

- 即時全面移行は行わない
- 最初にmanifestと依存関係試験を追加する
- inline bridgeを名前付きモジュールへ移す
- 新規機能は既存prototypeへの無秩序なmonkey patchを避ける
- 段階的にES Modulesまたはbuild済みbundleへ移行する

### GAP-P1-02 機械検証可能なJSON Schema不足

仕様書にはデータ辞書があるが、`schemas/save.schema.json`等の機械検証ファイルは確認できない。

対応方針:

- 現行v9スキーマをまず緩やかに定義する
- 必須項目と追加許容項目を区別する
- import時、移行後、保存前の3段階で検証する
- schema変更とmigration追加を同一PRにする

### GAP-P1-03 ログとテレメトリの実装統一

現状では`console.error`等による局所ログが中心で、仕様で定義した構造化イベント、相関ID、障害レポート形式との統一は未確認である。

対応方針:

- `Logger`インターフェースを追加する
- save、week advance、finance、migration、UI bootへ相関IDを渡す
- 個人情報を送信しない
- 初期段階はローカル診断レポート出力を優先する

### GAP-P1-04 リリースゲートの一本化

`test:release`、`test:release:balance`、`test:release:hardening`は存在するが、仕様上の全ゲートと実スクリプトの対応表が必要である。

対応方針:

- ゲートIDを付与する
- 各ゲートが実行するコマンドを文書化する
- 必須、nightly、手動を区別する
- 実行結果をartifactへ保存する

## 9. 矛盾解消の決定事項

本監査時点で、以下を正式な解釈とする。

1. 現行実運用のセーブ版はv9とする
2. `SAVE_KEY`は`capitalism_tycoon_web_v1`を維持する
3. `engine.js`のv8は移行元実装であり、将来は正本定数から分離する
4. 決定論は売上計算だけでなく、ID、人物生成、イベント生成、競合判断を含む
5. Node長期試験とPlaywright E2Eは代替関係ではなく、両方必須とする
6. マスター由来データのランダムUUID生成を将来仕様として認めない
7. 会計モジュールを経由しない会社現金・個人現金の直接変更を原則禁止する

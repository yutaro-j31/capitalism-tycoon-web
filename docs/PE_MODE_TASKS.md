## 全タスクで必ず守ること

以下はこのリポジトリの絶対条件。**どのタスクでも例外なく守る。**

- `SAVE_KEY` は `capitalism_tycoon_web_v1` のまま変更しない
- `saveVersion` は `9` のまま。マイグレーションが必要な設計にしない
- **旧セーブ互換**を壊さない。新規stateはトップレベル追加か任意フィールドにし、
  未定義時は既存挙動と完全に一致させる
- **決定論を壊さない**。`Math.random()` を新規に呼ばない。
  `js/ma-deal-room.js` の `hash()` / `unit()` / `between()` と同じハッシュ方式を使う。
  既存のRNG消費順序を変えない
- 会計整合性を壊さない。現金・資産・損益の増減は既存の `finance.event()` 経由で記録する
- 会社資産と個人資産の分離を維持する
- 配列は上限を設けて `slice` する（既存の方針に合わせる）
- iPhone Safari で動作する構成を維持する
- 既存の release / canonical / WebKit ゲートを弱めない
- **表示だけ追加して計算と連動しない状態を作らない**
- 各タスクで `tests/` にテストを追加する

# フェーズA: 入札システム（既存 ma-deal-room の拡張）

このフェーズは既存の `js/ma-deal-room.js` を土台にする。
設計書 §8 の通り、隠された真の価値（`maTargetTruthByID`）、観測値のブレ、
DD scopes、推奨価格レンジ、売り手の事情は**すでに実装済み**。それを壊さず拡張する。

## T1. 競合PEロースター

**前提:** なし（最初のタスク）

**内容:**
- 新規モジュール `js/pe-rivals.js` を作る
- `state.peRivals` に5社の固定ロースターを持たせる。旧セーブでは空配列で無害
- 各社の性格は設計書 §5「競合PEの性格」の表に従う

| ファーム | 出現条件 | 攻撃性 |
|---|---|---|
| 外資系大手 | 大型案件のみ | 1.06 |
| 地場系 | 地元案件 | 1.02 |
| 再生特化 | 傷んだ会社 | 0.95 |
| 事業会社 | シナジーあり | 1.12 |
| 新興ファンド | 序盤のみ | 1.04 |

- 案件（`acquisitionTarget`）の属性から、どの社が参加するかを**決定論的に**判定する関数を提供する
- この段階では既存の入札処理を変更しない。判定関数とロースターのみ

**完了条件:**
- 同じ案件・同じ週なら常に同じ参加社が返る
- 旧セーブを読み込んでもエラーが出ない
- テスト: 参加判定の決定論性、5社すべてが何らかの案件で参加しうること

## T3. ラウンド構造

**前提:** T2

**内容:**
- `deal.status` に2つ追加する

  - `final_bid`（最終入札）: 金額と条件を同時に提示

- `ACTIVE` と `DEAL_DEADLINE_STATUSES` の各Setに追加する
- 各ラウンドで「進む / 降りる」を選べる。降りるのはいつでも無料

**完了条件:**

- 各ラウンドで降りられる
- テスト: 状態遷移、降りたディールが正しく終端化されること

## T4. 売り手選好タイプ

**前提:** T3

**内容:**
- 売り手に4タイプを持たせ、`sellerScore` に重みを足す

| 売り手 | 求めるもの | 効果 |
|---|---|---|
| 創業オーナーの引退 | 雇用維持・社名存続 | 約束すると後のリストラが封じられる |
| 大企業の切り離し | クロージング速度 | DDを省くと有利、だが誤差が残る |
| 破綻企業の債権者 | 現金一括 | レバレッジを使えない |
| 別PEからの二次売却 | 金額のみ | 純粋な価格勝負 |

- **最重要の実装方針:** 条件は「勝率を上げる装置」ではなく
  **「同じ勝率を安い値段で買う装置」**として作る。
  条件を飲むと売り手評価が上がる分、**札そのものを約11%下げられる**設計にする。
  条件を飲んで札も高いままにすると、勝ちやすくなるだけで勝者の呪いが増し逆効果になる
  （設計書 §9 失敗5）
- 飲んだ条件は `deal.acceptedTerms` に記録し、後で参照できるようにする

**完了条件:**
- 条件を飲むと、より低い札で落札できる
- 飲んだ条件が記録され、買収後に参照できる
- テスト: 各売り手タイプで条件の効果が出ること

## T6. トラックレコードとGP出資

**前提:** T5

**内容:**
- Exit時（会社売却・IPO・子会社売却）に4項目を記録する
  - 実現額（`personalCash` の増分）
  - 個人MOIC（Exit額 ÷ 創業時投下額）
  - 所要年数（`week` の差分）
  - 事業の質（黒字継続週数・従業員数）
- 合成してトラックレコードスコア（0〜100）。**初回Exitでは5〜15点**
- 要求GP出資比率: `20% − 18% × (score/100)^0.7`
- 報酬条件: 管理報酬 `1.5% + 1.0% × score/100`、
  成功報酬 `15% + 10% × score/100`、ハードル `10% − 2% × score/100`
- **GP出資は回収不能**。失敗すれば個人資産も消える
- PEモードの解禁条件: Exit経験1回以上

**完了条件:**
- 初回Exit後にPEモードが解禁される
- スコア5で組成可能額が個人資産10億に対して約28億になる
- テスト: スコア計算、GP出資比率の曲線、解禁条件

## T7. DPI / IRR と次号組成

**前提:** T6

**内容:**
- DPI（実現分配 ÷ 出資総額）と IRR を計算する
- 次号を組成できる条件: **DPI 1.2倍以上 かつ 資金消化80%以上**
- 未投資返却はDPIを下げない（1.0で戻る）が、**トラックレコードに加算されない**。
  これが「損はしていないのに前に進めない」焦りの源
- LP信頼度（次号の調達上限に掛かる係数）
  - DPI 1.2以上: ×1.12
  - DPI 1.0〜1.2: ×0.80
  - 元本割れ: ×0.55

**完了条件:**
- 実績が出ると次号が組成でき、規模が伸びる
- 資金消化80%未満だと実績が加算されない
- テスト: DPI計算、次号組成の条件判定、LP信頼度の増減

## T8. LP面談

**前提:** T7

**内容:**
- **LP面談は「決定」として作らない**（設計書 §9 失敗7）。
  検証の結果、LP構成をどう調整しても「集められるだけ集める」が常に最適だった。
  面談は**進捗の可視化・前号への評価・約束の管理**を担う
- 5種類のLP。会える条件は設計書 §3 の表に従う
- 付帯条件は**制約ではなく約束**として扱う。守れないと次号で不利になるだけ
- 既存LPは自動継続。前回の約束を守れたかで態度が変わる
- LPの要求は断れる（金額が減るだけでペナルティなし）

**完了条件:**
- 実績に応じて会えるLPが増える
- 約束の達成状況が記録され、次号の調達額に反映される
- テスト: LP解禁条件、約束の記録と反映

# フェーズC: 案件と制約

## T9. スロット制約とチーム

**前提:** T5

**内容:**
- **チーム上限は管理報酬から自動的に決まる**（1人あたり年2000万円）。
  制約を別途設ける必要はない
- **チーム上限は60人で固定**。超過分の管理報酬は素直に利益にする
  （現実の大型ファンドもフィーだけで儲かる。設計書 §9 失敗6）
- スロット数の上限は2つで決める
  - 1件あたりの下限投下額
  - LPの分散義務（1件はファンドの25%まで）
- 結果、スロットは **2 → 4 → 6 → 8** で頭打ち
- 注意分散: `attention = チーム人数 ÷ 案件数`。1件あたり1人を割ると改善が鈍る
- **保有期間: 1号は4年、2号以降は3年**が最適
  （1号は再投資できないので機会費用がゼロ）

**完了条件:**
- 28億のファンドで自分＋1人しか雇えず、スロットが2〜3件になる
- 1件あたり1人を割ると改善効果が落ちる
- テスト: チーム上限の算出、スロット上限、注意分散の効果

## T11. 業種4帯

**前提:** T9

**内容:**
- 案件生成を4帯に分ける。詳細は設計書 §15

| 帯 | 規模 | 取得倍率 | レバ | 腕の乗り |
|---|---|---|---|---|
| 5本柱系 | 20〜1,500億 | 8.0 | 3.5 | **0.28** |
| 小型承継 | 3〜40億 | 5.5 | 4.5 | 0.04 |
| 中型 | 30〜400億 | 7.0 | 4.0 | 0.12 |
| 大型 | 300〜4,000億 | 8.5 | 3.5 | 0.10 |

- **リターンを削らず、規模帯で棲み分けさせる。**
  小型承継は大型ファンドでは消化できない（分散義務と最低投下額で自然に効く）
- 出口の可否
  - 5本柱系: 売却 / IPO / **自分で経営**
  - それ以外: 売却 / IPO（対応する株式市場セクターがある帯のみ）
- **案件数は年4件で固定。市況は数ではなく中身（質）を変える**
  - 好況: 優良案件が高値で出る。買い手も多い
  - 不況: 傷んだ案件が安く出る。買い手が減る
  - **年1件まで落とさないこと。腕が完全に消える**（設計書 §5）

**完了条件:**
- ファンド規模に応じて打てる帯が変わる
- 年4件が維持される
- テスト: 帯ごとの案件生成、規模による絞り込み、供給数の下限

## T12. 共同投資

**前提:** T7, T11

**内容:**
- LPが案件ごとに追加出資する仕組み
- 枠はファンド規模の**1倍**まで
- 共同投資分のキャリーは**フルの半分**（実績次第で 7.5〜12%）。
  **ゼロにすると機能が死ぬ**（規模の逓減で質が落ちるのに収入がなく、手間だけ増える）
- 管理報酬は共同投資分にはかからない
- 解禁は実績連動（数値上は不要だが体験として）
- 案件ごとに「共同投資を入れる（規模を取る）」「全額ファンドで打つ（報酬率を取る）」を選べる

**完了条件:**
- 共同投資で分散義務を超える大型案件が打てる
- 共同投資分の報酬が半分になる
- テスト: 枠の上限、報酬計算、分散義務との関係

# フェーズD: 人脈と経営

## T13. 人脈4経路

**前提:** T11

**内容:**
- 新規モジュール `js/pe-network.js`
- `state.peNetwork = { nodes: [], weeklyActions: 2, favorsOwed: [] }`。`nodes` は上限100
- **人脈は金で買えない。通貨は時間（週次アクション枠2回）**
- 4経路。詳細は設計書 §6.5

| 経路 | 通貨 | 上限寄与 |
|---|---|---|
| 紹介者（銀行・会計士） | 取引関係 | 22% |
| 長期の仕込み | 時間 | 55%（成功時） |
| 業界での評判 | 経営実績 | 32% |
| 既存投資先からの紹介 | 改善スコア | 30% |

- **1案件あたりの独占上限は40%**。構造的な縛り（業種・地域）だけでは48%まで伸びるため必須
- **紹介者には年5ポイントの減衰を入れる。** 入れないと最も安直な経路が全体の半分を占める
- 独占案件は「安く買える」ではなく**「独占交渉権」**。
  期間内にまとまらなければ公開入札に流れる
- ノードの供給源は5本柱の経営（仕入先、テナントオーナー、銀行支店長、雇ったCXO、Exit先の経営陣）
- **腕による格差は意図的に許容する。** 下手は独占0%、普通は投資先紹介0%で構わない

**完了条件:**
- 4経路それぞれが独立に育つ
- 独占比率が40%を超えない
- 紹介者が減衰する
- テスト: 各経路の判定、上限、減衰

## T16. 案件供給とDD枠の結線

`generateAnnualDeals()`（T11）を週次エンジンから `state.acquisitionTargets` に流し込み、
`consumeDDSlot()`（T10）をPE案件のDD開始トランザクションに接続した。年4件、決定論的。
PE案件は `peTierID` / `dealChannel` で通常のM&A候補と識別し、期限は既存の
`DEAL_DEADLINE_STATUSES` に乗せる。DDにはファンドの指定を必須とし、枠が尽きたら拒否する。

## T17. ファンド資金による取得とExit決済

入札に勝った案件を**ファンドの現金**で取得する経路を作った。会社の現金は動かず、連結子会社
にもならない。スロット満杯（T9 `slotCapacity`）で取得を拒否する。Exit決済のウォーターフォール
（元本返済 → ハードル → メインのキャリー → 共同投資分は半分 → 二重徴収防止 → GPのキャリーは
個人資産へ）を実装し、`evaluateFund()` を週次処理から呼ぶようにした。

保有企業の企業価値は**入札価格ではなくT11の本来の企業価値**を使う（高く買うほどMOICが下がる。
入札の判断が3〜4年後に返ってくる因果をここで成立させる）。

## T18. 買収先経営の6レバー化

6レバー = 価格 / 品質 / 拠点（出店と再編）/ 仕入れ・調達 / 人件費と人員 / 商品構成。
コスト側は即効、商品構成は2.5年で立ち上がる。削りすぎた副作用は1年〜3四半期遅れて客数に返る。
T4で飲んだ雇用維持の約束がある案件では人員削減と閉店を禁止し、約束が無くても実行すれば
業界の評判（T13経路3）が下がる。attention倍率（T9）は週次EBITDAに一度だけ乗る。

## T19. 人脈ノードの生成結線

設計書§6.5の供給源6種（店舗の仕入先 / テナント契約 / 銀行借入 / 雇ったCXO / Exit先の経営陣 /
IPO時の証券会社）を既存アクションのフックとして実装した。同じ相手は二重に入らず、失敗した
アクションではノードが生まれない。`monopolyProbability()` / `rollMonopolySourcing()` を案件供給に
接続し、独占案件（`dealChannel='monopoly'`、競らずに買えるぶん12%安い）を供給する。
独占確率は1案件あたり40%を超えない。週次アクション枠（2回）を消費する接触操作を追加した。

## T20. 通し検証（100年・production経路）

`scripts/pe-mode-100y-verification.js`（**リポジトリ内**）。production の週次エンジンと本番の
入札・取得・経営・Exit経路のみを呼び、スクリプトが持つのはプレイヤーの判断だけ。
3つのスキルレベルは**同一のポリシー枠組み**で、判断の質だけが異なる。

検証で3つの較正ミスが判明し修正した（品質投資が実質タダ / 出店1件で全社EBITDAが倍 /
Exit価格が6レバーの結果を無視）。いずれも会社の規模を無視した価格付けで、100年で資産が
京のオーダーまで指数爆発する原因だった。

## T21. GP出資の会計とファンド組成の入口

`createFund()` が `fund.cash` を作る一方で `personalCash` もLP資本も減らさず、**無から現金が
生まれていた**。組成を1トランザクションにし、次の保存則を成立させた。

```
personalCash_after + fund.cash === personalCash_before + fund.lpContributed
```

Exit分配・未投資返却の**GP持分が個人資産へ戻る**ようにした（従来はキャリーだけ）。
プレイヤーがファンドを組成する production アクション `formPEFund()` を追加し、PE案件のDDが
UIから開始できない問題（fundIDが渡らない）も解消した。

## T22. ファンドの梯子の停止を解く

ファンドが育つと `eligibleTiers()` が空を返し、案件が1件も供給されず資金消化率が固定され、
次号ゲートを二度と満たせなくなっていた（年20前後で停止、以後80年成長ゼロ）。
帯のフォールバック、規模に応じた消化率要件の緩和（DPI 1.2の要件は不変）、そして
**市場が吸収できる規模**（年4件×5年で消化できる額。約8,079億円）による組成額の頭打ちで解いた。

## T23. リターンの再較正

Fund I DPI中央値 2.48 / Fund II到達率 100% と設計値より甘く、「腕が普通でも15%は足踏みする」
という緊張感が消えていた。**上振れだけを抑える**方向で較正（改善スコアの物差しを厳しく、
品質投資の効果に天井、出店の増分を縮小、Exit倍率は下限を0.70→0.80に上げ上側の幅を圧縮、
市況をExit価格にも対称に適用）。結果: DPI中央値1.35 / Fund II到達率85〜86% / 半減0.0%。

## T24. ロックアウトの解消と上限の再設定

次号ゲートが最新ファンドだけを見るため、1本でもDPI 1.2を下回ると**恒久的に**次号を組めなく
なっていた。設計書§10の救済導線（起業に戻ってExitする）をゲートに接続した（新しいExit2件＋
スコア+10。DPI 1.2の要件は不変）。あわせてファンド1本の上限を**5兆円→1兆円**に変更した
（年4件×§15の帯では5兆円は構造的に消化できない）。設計書§2/§10/§12を改訂し、§16.5に
検証ログを新設した。

## T25. 積み残しの整理

本ファイルのリポジトリへの取り込み、上限なし配列4件（`shareholderEventLog` /
`mediaActionLog` / `industryAwards` / `ventureForumEvents`）への共通200件キャップ、個人資産の
利回り上限（設計書§12の年3%）の実測と対処。4配列とも書き込み・normalize・週次処理・旧セーブ
読み込みで同じ凍結済み上限表を通り、新しい順を維持する。

## T26. 会計モデルの完成（実装済み）

共同投資は設計書§14どおり案件ごとのLP追加拠出と確定し、`coinvestContributed` →
`coinvestCash` → 売り手というcash pathを追加した。Exitでは共同投資の元本・利益から半分carryを
一度だけ控除し、ファンドDPIとは分離した`coinvestReturned`へ返す。

管理報酬は年次周年ごとに、ファンドcash（payer）からGP法人である会社cash（receiver）へ移す。
`lastManagementFeePeriod`とfinance idempotency keyで同一期の二重払いを防ぎ、現金不足分は
`managementFeeShortfall`として記録するだけで未払cashを生成しない。LP/GP分配、GP carryも
`lpDistributed` / `gpDistributed` / `gpCarryPaid`に分け、個人・会社・ファンド・共同投資家の
ownership claimを混ぜない。追加フィールドはすべてsaveVersion 9のoptional defaultとして旧セーブ
読み込み時に補完される。検証値と実装コミットは本PRの最終検証ログに記録する。

会計修正だけを入れた状態でFund Iをproduction週次経路により60 fixed seeds（各10年）再測定した。
DPI中央値1.27 / P10 1.07 / P90 1.56 / DPI 0.6未満0.0% / Fund II到達70.0% / 平均保有4.44年。
旧較正（中央値1.35、Fund II 85〜86%）より下がり、中央値1.3〜1.7・到達80〜90%の設計rangeを
外れた。これは実在する管理報酬をファンドcashから支払うようにした直接の結果であり、会計を
崩して旧値へ戻さず、係数の再較正を別balance taskへ送る。

100年production実測（同一seed 12345）は、上手/普通/下手の順に総資産2.70兆/1.26兆/
0.292兆、個人資産1.49兆/0.293兆/0.032兆、ファンド15/9/8本、最大ファンド0.808兆/
0.808兆/0.473兆だった。上手 ≥ 普通 ≥ 下手、下手は上限未到達、全runでNaN/Infinityなし。
累計の管理報酬は1.13兆/0.640兆/0.303兆、carryは1.04兆/0.074兆/0.001兆、共同投資は
拠出2.27兆→返還3.74兆 / 1.64兆→1.93兆 / 1.40兆→1.25兆。最大saveは2,778,051 bytes
（2.65MB、T25の2,785,421 bytesから7,370 bytes減）。seed 999の100年runを2回行い、最終state
SHA-256 `7e8dba6b91eaac959337f7923f500e2c...` が一致した。

# 機能要望メモ

オーナーから寄せられた要望と、その実装可否を検討した結果を貯めるファイル。
Manus や ChatGPT など他のツールで考えた案を持ち込む運用があるため、
その都度ここへ追記し、着手前に「現状どこまで実装済みか」を確認する。

`docs/gameplay-systems-roadmap.md` は計画済みフェーズを管理する場所で、
このファイルは着手前の要望と調査結果を置く場所。役割が違う。

## 記録するときの型

要望ごとに次の3つを書く。「現状」を省略しない。既に実装済みの機能を
新規実装として作り直す事故を防ぐのがこのファイルの主目的。

- **要望**: オーナーの言葉に近い形で残す
- **現状**: 既存実装を調べた結果（機能名・ファイル・どこまで動くか）
- **見立て**: どう実装できるか。既存資産を流用できるなら何を流用するか

## 全体の構造的な傾向（2026-08-14 調査）

会社側の機能は非常に厚く、個人側の同種機能は薄い、という非対称が
一貫している。オーナーの「個人資産の使い道を深く追求したい」という
要望は、この落差そのものを指している。

| 領域 | 会社側 | 個人側 |
| --- | --- | --- |
| 不動産 | 46モジュール（テナント契約・保証金・滞納・保険・修繕・再開発・管理プラン・担保融資・税制・CAPEX ROI） | `buyPersonalRealEstate` / `sellPersonalRealEstate` のみ。週次で家賃が入り資産価値が変動するだけ |
| 買収後の経営 | PMI 100日計画・長期ガード・子会社KPI・業績レビューなど多数 | `improvePEDeal` のみ。個人資金を払うと `improvementScore+6`・評価額`×1.05` を繰り返すだけ |
| 資本政策 | 増資・社債・転換社債・優先株・自社株買いなど | 個人株式は保有と売買のみ |

**この非対称は、個人側の作り込み余地であると同時に、実装上の近道でもある。**
会社側に既にある厚いモデルを個人側へ適用する形にすれば、ゼロから作るより
早く、挙動の一貫性も保てる。ただし CLAUDE.md の不変条件
「会社資産と個人資産の分離を維持」は必ず守り、共有するのは計算ロジックだけで、
資産・現金の帰属は必ず分けること。

## 要望一覧

### R1. VC 的な遊び方を厚くする

- **要望**: Coffee Inc 2 では資金を株式で運用したり、エンジェル投資・ベンチャー
  投資で増やす遊び方をしていた。そこをやり込み要素として厚くしたい。
- **現状**: 骨格は既にある。
  - `createAngelInvestment` / `exitAngelInvestment`（エンジェル投資）
  - `attendVentureForum`（案件発掘）
  - `startups`（3件、Seed/評価額/成長率/リスク/ランウェイ/ラウンド情報を保持）
  - `startupFundingHistory`（ラウンド履歴）
  - `personalStocks`（個人株式の保有）
  - 内部ベンチャー系（`fundInternalVenture` / `spinOffInternalVenture` / `sellInternalVenture`）
- **見立て**: 新規実装ではなく既存の深掘り。候補は
  (a) スタートアップが3件固定なので、週次で案件が入れ替わる案件フロー、
  (b) ラウンド（Seed→Series A→…）に応じた希薄化とフォローオン投資の判断、
  (c) 個人株式のポートフォリオ指標（分散・ボラティリティ・実現損益の推移）。
  `startups` は既に `fundingRound` / `fundingOpen` / `runwayWeeks` を持つので、
  (b) が最も既存構造に乗る。
- **進捗**: 既存保有先の追加資金調達ラウンド、標準VC希薄化、会社・個人別の
  pro-rataフォローオン判断を実装。ラウンド条件は開始時に固定し、終了時に評価額と
  stage別runwayを更新する。
  - **(a) 案件の自動入替を実装**（`refreshStartupDealFlow`、`js/expansion.js`）。
    `g.startups`が固定3件で一度死亡・IPO退出すると投資先が二度と増えなかった問題を
    解消。開放中（生存中・未子会社化・未IPO）の案件数が3件未満のとき、新規プール
    （6件）から案件が追加される。トリガー確率は`founderNetworkLevel`
    （`investFounder('network')`/`attendVentureForum`で既に上昇するが従来は
    何にも使われていなかった個人ステータス）で変動し、この既存ステータスに
    初めて実効果を与えた。`openCount>=3`のときは`&&`の短絡評価でRNGを一切
    消費しないため、通常プレイでは`randomCallsAtWeek52`・市場キャリブレーションの
    指紋に影響しない。
  - **(創業者・チームの詳細DD)を実装**（`conductStartupDueDiligence`、`js/expansion.js`、PR #436）。
    個人資金でminTicketの5%を払い、評価（優良/普通/要注意/危険）・評価額割引（0〜15%）・
    懸念点を可視化する。評価は当初、案件IDのハッシュのみから導出しており実際の
    `growth`/`risk`と無相関だったため、「危険」判定ほど得というフリーアルファの
    抜け穴になっていた（PR #441で実fundamentals70%＋ノイズ30%へ修正し是正済み）。
  - **VCファンド／LPを実装**（`PERSONAL_INVESTMENT_OFFERS`の`vc-fund`、PR #437）。
    既存の`personalInvestments`機構（`buyPersonalInvestment`/`sellPersonalInvestment`＋
    週次mark-to-market）へ、含み益にのみ20%キャリーを課す商品として追加。
  - **セカンダリー市場を実装**（`sellStartupSecondary`、`js/expansion.js`、PR #438）。
    非公開・生存中のVC持分を評価額から流動性ディスカウント（12〜28%）を引いた金額で
    早期売却できる。売却前に金額プレビュー付き確認ダイアログを表示する
    （`previewStartupSecondarySale`、PR #443）。
  - **既知の落とし穴**: 詳細DDの評価額割引とセカンダリー売却を安易に組み合わせると、
    週を進めずに`invest→sell`往復で無限に現金を増やせる不具合が一度発生した
    （PR #439で修正、`sellStartupSecondary`もDD割引後の評価額を使うよう統一し、
    会社側の`idempotencyKey`に連番を含めて同週複数売却の会計不整合も同時に解消）。
    今後この2機能の計算式を個別に変更する際は、往復取引が黒字化しないことを
    再度確認すること。
  - 個人投資商品全般の`risk`パラメータが`weeklyReturn+rand(-risk,risk)/20`という
    過剰減衰で実質機能していなかった問題も発見・修正済み（`/5`へ変更、PR #442）。
    vc-fundと他商品の再バランスは、このrisk修正だけで実質解消したため見送った
    （`weeklyReturn/risk`比で見るとvc-fundは修正後、5商品中最もリスク調整後
    リターンが低く、正当なリスクプレミアムの取引になっている）。
  - R1の残タスクはこれで完了。

### R2. TOB / MBO した会社の業績を伸ばす・再建する

- **要望**: TOB や MBO で取得した会社の業績をさらに伸ばしたり、再建したりできる
  ようにしたい。
- **現状**: 取得までは厚いが、取得後が薄い。
  - 取得: `createPEDeal` / `executeMBO` / `squeezeOutListedSubsidiary` /
    `acceptInboundBuyoutOffer` / `openMADealRoom`
  - 取得後: `improvePEDeal` のみ。内容は「個人資金を払う→`improvementScore+6`、
    評価額`×1.05`」の繰り返しで、選択も失敗も無い。
- **見立て**: **落差がいちばん大きく、いちばん作り甲斐がある。** 会社側には
  PMI 100日計画・`subsidiary-budget-kpi`・`subsidiary-performance-review` が
  既にあるので、その構造を個人PEディールへ適用する。
  施策を単一ボタンではなく「コスト削減／人材入替／設備投資／販路拡大」など
  複数の選択肢にし、対象企業の状態（過剰債務・人材流出・老朽設備）に応じて
  効く施策が変わる形にすると、再建としての手応えが出る。
- **進捗**: `js/pe-value-creation.js` として着手済み。
  - 課題4種（高コスト体質／人材流出／設備老朽／販路縮小）と施策4種を実装し、
    課題に的中する施策だけが大きく伸びる形にした（#409）
  - 改善度をEXIT価格へ反映（改善度100で+50%、未改善は従来どおりの価格）（#410）
  - 施策に失敗確率と副作用を追加。失敗しても費用は取られ、改善度と企業価値が
    後退する。失敗率と痛手は施策ごとに違え、確率が最も高い施策と痛手が最も
    大きい施策を別々にしてトレードオフにした
  - 課題も成否も**保存せず導出**している（`deterministicUnit` による FNV-1a）。
    乱数を引かないので決定論の指紋は動かず、セーブ&ロードで結果を引き直せない。
    成否の鍵に週を含めたので「同じ週の打ち直しは同じ結果、週を進めれば再挑戦」
    という挙動になる。この導出方式は R1・R4 へも流用できる
  - **週次業績を改善度と連動させて実装**（`weeklyRevenueFor`/`marginFor`/
    `weeklyProfitFor`、PR #445）。`weeklyRevenue`は取得時のinvestedAmountに
    対する固定割合（3%/週）で一度だけ確定し、市場ノイズと無関係に改善度だけで
    動くようにした。`marginFor`は既存の`EXIT_BASELINE_SCORE`（=20）を基準に、
    改善度から利益率を導出する。基準点では-3%（未改善の再建案件は実際に
    赤字を垂れ流す）、改善度100で+12%（黒字転換）。会社保有案件は
    `finance.event`で台帳にも記帳し、個人保有は他の個人資金フローと同様
    台帳を一切通さない。
  - **施策効果の遅延と複数案件同時進行時の経営資源の取り合いを実装**
    （`pendingInitiative`/`resolvePendingInitiatives`/`INITIATIVE_DELAY_WEEKS`/
    `MAX_CONCURRENT_INITIATIVES`、PR #446）。`applyInitiative`は費用支払いと
    成否判定（既存の決定論的`outcomeRoll`、コミット時点のweek/scoreで確定）は
    その場で行うが、`improvementScore`/`currentValuation`への反映と結果通知は
    2週間遅延させ、週次ループで解決する。1案件につき同時に持てる進行中施策は
    1件のみ。同一オーナーアカウント（会社2件・個人1件、会社/個人は独立集計）
    内で同時進行できる案件数にも上限を設け、経営資源の取り合いを表現した。
  - R2の残タスクはこれで完了。

### R3. スポーツ球団経営を厚くする

- **要望**: Coffee Inc 2 のスポーツ球団経営をやり込み要素として厚くしたい。
- **現状**: 想定より厚い。`draftPlayer` / `tradePlayer` / `refreshSportsMarket` /
  `toggleTeamSale` / `acceptTeamSaleOffer` があり、`sportsDraftCandidates` /
  `sportsTradeMarket` / `sportsSaleOffers` を state に持つ。
  `SPORTS_TEAMS` のマスタは3件で `{price, revenue, cost, prestige}`。
- **旧記述の訂正（2026-08-18 監査）**: 以前ここに書いていた「成績が収益へ与える
  影響が薄い」は**不正確だった**。`teamStrength → 勝敗 → fanBase → 週次収益` の
  ループは `updatePersonalAssets`（js/engine.js）に最初から存在していた。
  実際に欠けていたのは**下向きの圧力**のほうで、選手を獲得すると `teamStrength` が
  一括払い1回で恒久的に上がる一方、週次費用はマスタの定数のまま1円も増えなかった。
  つまり「出てきた選手を全部買って `teamStrength` を100に張り付かせる」のが常に
  正解で、最初の数週間を過ぎると意思決定が残らない構造だった。
- **実装済み（PR #448、`js/sports-management.js`）**:
  - **選手の週次年俸**。ドラフト／トレード／外国人補強の3経路すべてで獲得時に
    `weeklySalary` を保存し、強い戦力が恒久的に重い人件費になるようにした。
    `signForeignPlayer` は従来 `teamStrength` を上げるだけでロスターに誰も
    追加しておらず、継続コストが完全にゼロだったのでこれも塞いだ
  - **収益を入場料とスポンサーに分離**。入場料は `fanBase`、スポンサーは
    **前シーズンの勝率**に連動する。スポンサーが1シーズン遅れることで、今季の
    出費を来季の収入で回収するという時間差が生まれ、強化が「即座の見返り」
    ではなく「賭け」になる
  - **シーズン成績**。`seasonGames` を `seasonWins` と並べて持ち、52試合ごとに
    勝率を `lastSeasonWinRate` へ確定してリセットする。`seasonWins` は従来
    カウントアップするだけで何にも読まれていなかった
  - バランスは実測で調整（無補強で放置 約1.0M/週、13人補強した強豪 約3.6M/週、
    弱小は赤字）。**2回作り直している**。1回目は年俸が重すぎて選手3人で即赤字に
    なり「誰も獲得しない」が正解になった。2回目は戦力カーブが緩すぎて最大化に
    24人必要になり、その人件費が収入の伸びを食い尽くして強豪が無補強より
    稼げないという真逆の状態になった。バランス値を変えるときは、この2つの
    失敗方向のどちらにも倒れていないかを必ず実測で確認すること
- **先に直した不具合（PR #447）**: R3着手前の監査で、会社保有球団の週次収支が
  `finance.event` を通っておらず1週で `finance.validate()` が落ちること、および
  `personalNetWorth()` が全球団を owner 無視で計上する一方 `companyValue()` が
  球団を一切計上せず「会社資金で個人資産が増える」状態になっていたことを発見し
  修正した。`finance.js` の `otherFixedBook()` は既に `owner==='company'` で
  フィルタしており、台帳とエンジンで所有者の判定が食い違っていた
- **将来候補**: 放映権・グッズなど収益源の追加、スタジアム投資、選手の年齢と
  衰え、シーズン順位表とリーグ戦、監督・コーチ。

### R4. 個人の不動産投資を厚くする

- **要望**: 不動産投資をやり込み要素として厚くしたい。
- **現状（2026-08-19 時点）**: 賃貸運営・住宅ローン・固定資産税・短期賃貸まで実装済み（下記参照）。
  なお不動産には2系統あり、R4の対象は `g.personalRealEstateHoldings` のほう。
  `g.properties` は会社側46モジュールが動く別系統で、`ownerOf()` に personal 分岐は
  あるものの `owner==='personal'` の物件を作る経路が実質無く、事実上会社専用。
  混同すると「個人不動産に融資が無い」を `g.properties` 側で直そうとして空振りする。
- **見立て**: **会社側の46モジュールとの落差が最大。** 会社不動産のモデル
  （テナント契約・空室・修繕・保険・担保融資）を個人側へ段階的に適用できる。
  一度に全部ではなく、まず「テナントが付く／空室になる」だけでも体験が変わる。
  流用時は資産と現金の帰属を必ず個人側に閉じること。

- **実装済み（個人賃貸運営）**: 個人保有物件に、入居・空室、3種類の契約更新戦略、決定論的な更新/退去/再入居、固定維持費と管理費、状態劣化と手動修繕、入居率、累計家賃・運営費・NOI、表面利回り・実効利回りを追加。旧saveは読み込み時に書き換えず、次の週次処理で安全に運営状態を開始する。
- **実装済み（住宅ローン／レバレッジ）**（`js/personal-real-estate-mortgage.js`、PR #450）:
  物件を担保に借り入れられる3商品（固定4.2%/LTV60%、変動 policyRate+2.2%/LTV70%、
  低LTV長期3.4%/LTV45%）。週次で利息＋元本均等を返済し、繰上返済も可能。
  変動金利は既存の `policyRate` に連動するので、いま最も安い融資が後で最も高くなりうる。
  **これをタダの金にしないのが差押え**で、8週連続の返済不能で物件を失い、市場価格85%での
  売却で残債を清算、不足分は個人負債として残る。借金が漏れる3経路
  （純資産から残債を引かない／売却で借金が消える／差押え済み物件が計上され続ける）は
  すべて塞いであり、ミューテーション試験で担保している
- **実装済み（利回りとローン期間の是正）**（PR #451）: #450 を**実測して**見つかった2件の是正。
  - **ローン期間が致命的だった**。返済8〜12年では元本均等返済が家賃を上回り、
    満室でも週 -66,646円。稼働が良くても現金が減り続け必ず差し押さえられる、
    機能として使えない状態だった。25〜35年へ延長し、入居中 +42,055円/週 ・
    空室時 -96,644円/週 という、差押えルールが本来想定していた形にした
  - 表面利回り17〜18%（NOI 15〜16%）→ 表面8.0〜9.0%（NOI 7.0〜7.9%）へ。
    どの金利より高すぎてレバレッジが無条件に正解だった状態を解消。既存セーブの
    保有物件は自身の `weeklyRent` を持つため影響しない
  - **バランス測定の落とし穴**: 単一seed・2年で測ると借入併用が純資産マイナスに見えたが、
    市況の下降局面を引いただけだった。2seed・1年では現金のみ +28.5M に対し
    借入併用 +63.4M。**1回の測定では機構の性質と市況を区別できない**
- **実装済み（固定資産税）**（`js/personal-real-estate-taxes.js`、PR #452）:
  評価額に対し年1.4%（日本の標準税率）を四半期分割で課税。保有週数基準なので
  年度途中購入でも保有していない四半期は請求されない。未納は可視化して次回請求へ
  繰り越す。**空室でも課税される**のがこの機能の要点。会社側は3税制を持つが個人は
  一律1.4%にした — 高い物件に高税率を当てると利回り差とほぼ完全に相殺され、
  3件が0.4ポイント以内に収まって物件選択の意味が消えるため
  - 売却時の未納分は売却代金から精算される（PR #457）。未納を抱えたまま売り抜けて
    債務を消せる穴を塞いだもの
- **調査済み・調整不要（2026-08-19 実測）**: 物件価値の週次変動
  `currentValue*(1.0005+(cycle-1)*.05)` について、以前ここに「年率-53%〜+187%で
  極端」と書いていたが、これは**cycleが clamp の両端（0.70/1.40）に張り付いた
  場合の理論値**であり、実際には到達しない。cycle は
  `(realEstateCycle+economy)/2` で、realEstateCycle 自体が週 ±0.01 の
  ランダムウォークなので、2年でも概ね ±0.1 程度しか動かない。
  実測（2年）では cycle は 0.78〜1.17 に収まり、物件価値は購入時比で
  最高+25% / 最低-13%。会社名を変えて経済シナリオを変えても1年で+17%〜+27%程度で、
  不動産価格の変動として妥当な範囲だった。**係数の調整は行わない**
  - なお、この理論値を書いた時点では PR #454 の名前衝突バグが未修正で、
    cycle が毎週破壊されていた。壊れた状態の観測から極端な理論値を導いていた
  - **経済シナリオは `companyName` のハッシュで決まる**
    （`deterministic-economic-foundation.js` の `box.seed=hash(companyName)`）。
    プレイのRNG seedとは独立なので、同じ会社名なら誰が何度やっても同じ景気循環に
    なる。バランスを測るときにseedを変えても経済指標が動かないのはこのため。
    シナリオを変えたければ会社名を変える
- **実装済み（短期賃貸／運用方式の選択）**（`js/personal-real-estate-short-term.js`、PR #456）:
  物件ごとに長期賃貸／短期賃貸を選べる。短期は満室週が長期の2.8倍だが満室は例外で、
  稼働率が毎週「季節性＋建物の状態＋景気」から算出される。運営費は重く
  （実収入への手数料＋誰も泊まらなくても発生する常時費用）、宿泊客は単一テナントの
  2倍の速さで建物を傷める。切替には初期費用がかかり、**両方向とも13週ロック**される
  （週ごとに有利な方へ乗り換えられない）。稼働率は既存の `deterministicUnit`(FNV-1a)
  由来でRNGを消費しない
  - 実測（2年放置）: 長期は現金10.32M・建物状態77.5、短期は現金12.80M（+24%）・
    建物状態65.0。状態は稼働率に効くので、放置すると複利で悪化する
  - **緊張が効くのは既存機能との組み合わせ**。ローン返済も固定資産税も季節に
    無関心なので、レバレッジ物件を閑散期に短期運用すると赤字になる
    （不調週の手取66,856円に対し週次返済85,682円）
  - **バランス設定で踏んだ罠2件**（どちらも理屈では気づかず実測で発覚）:
    1. 常時費用を `.0016`（週次）に設定 → 年8.3%相当となり長期の維持費0.6%/年の
       **14倍**。短期の年間NOIが長期の**50分の1**になった。年次レートに見える
       数値を週次スロットに置いた取り違え。**この定数は週次**であることに注意
    2. 建物の劣化を `.06` と長期（`.12`占有時/`.08`空室時）より**遅く**設定 →
       短期の方が建物に優しいという逆転。`.24`（長期の2倍）へ修正
- **候補の監査結果（2026-08-19）**: 残りに着手する前に読むこと。
  - **REIT**: 既存の `createRealEstateVehicle`（`real-estate-complete-cycle.js`）は
    `g.properties`（会社物件）を束ねるビークルで、**個人が間接投資する手段ではない**。
    個人側は `personalInvestments` に商品を足せば済み、R1のvc-fundと同じ形になる
  - **減価償却の税務処理**: 個人の所得税・確定申告の概念が**存在しない**（grep 0件）。
    節税効果を表現するには税制の土台から作る必要がある
  - **不動産法人**: 「会社資産と個人資産の分離」という不変条件に直接触れるため、
    設計時点で分離の維持方法を先に決めること
  - **開発・再開発**: 会社側モジュール（`real-estate-development.js` /
    `real-estate-redevelopment-projects.js`）を流用できるが規模が大きい
- **将来候補**: 減価償却の税務処理、不動産法人、REIT、開発・再開発。

## この追補が加える中心命題

既存の「AIには実装・検証を任せ、人間はゲームルールと最終評価を主導する」という
原則は、AIへ渡す指示そのものも、モデルの能力に合わせて設計・棚卸しするという
原則によって補われる。

1. **過去モデル向けの「足場」を定期監査する**
   「毎回これを読む」「必ずこの手順」「毎回確認」といった常設指示は、以前の
   弱点を補うために蓄積されやすい。モデル更新時に、まだ必要かを棚卸しし、
   不要な手取り足取りを残さない。

2. **必要な文脈だけを条件付きで読む**
   全作業で全資料を読むのではなく、architectureは境界変更時、databaseは
   スキーマ変更時、deploymentは配備時、というように参照条件を明示する。
   コンテキストを「常設コスト」にしない。

3. **Skillは大きな手順書ではなく最小ルーターにする**
   Skillの名前・説明は短く適用条件を狭くする。詳細手順・参考資料・スクリプト
   は必要な時だけ読むprogressive disclosureとし、無関係なルールをタスクへ
   流入させない。

4. **承認境界は「全部聞く/全部自動」の二択にしない**
   使い捨てfixtureのローカルテスト、静的解析、依頼変更に起因する失敗修正
   など、安全な反復は事前許可できる。一方、破壊的変更・本番・外部公開などは
   明示的な承認境界として残す。

5. **作業開始前に「Done」を定義する**
   「実装した」で止めず、起動・実行・検査・失敗修正・再テストまで必要なら
   最初から完了条件へ含める。探索を続ける場合も、何を調べ、どこで止めるかを
   明示する。

**短い指示≠弱い統制。常設ルールを減らし、適用条件・権限境界・完了条件・
検証証拠を明確にする。**

## 資本主義ポケット TYCOONの開発環境への変換案

以下は上記記事の設計思想を本プロジェクトの開発環境へ変換した推奨規約案。
記事の直訳ではなく、既存の「決定論・会計整合・セーブ互換・モバイル優先」と
両立するよう再構成したもの。実際に採用するかは別途判断が必要。

| 領域 | 規約案 |
|---|---|
| 常設ルール | CLAUDE.md等には、長期に変わらない不変条件・安全境界・アーキテクチャ上の禁止事項だけを残す。タスク固有の手順を常設しない。 |
| 参照資料 | ルート文書は「どの条件で、どの資料を読むか」を示すルーターにする。詳細資料はsubsystem/変更種別ごとに条件付きロードする。 |
| Skill | 1 Skill=1明確な用途。説明文は短く、triggerを狭くする。複数workflowを抱える場合はrootを最小ルーター化し、詳細は別文書・scriptへ分離する。 |
| タスク依頼 | Goal/Scope/Acceptance Criteria/Non-goals/Approval Boundaryを開始時に定義する。「完成」の意味を実装・検証・配備のどこまでか明示する。 |
| 自律ループ | 安全なローカル環境では、focused test→原因特定→依頼変更に起因する修正→再テストを、逐次承認なしで完了まで回せるよう許可する。 |
| 承認が必要な境界 | 本番データ、破壊的migration、不可逆操作、外部公開・送信、認証情報、ゲーム経済の根本ルール変更などは別扱いとし、明示的な承認点を置く。 |
| モデル更新 | 大きなモデル更新時はinstructions auditを実施し、各ルールをKEEP/CONDITIONAL/MOVE TO REFERENCE/REMOVEに分類する。いきなり一括削除せず、監査結果を人間が確認する。 |
| 完了証拠 | 「done」だけを成果物にしない。変更差分、実行したテスト、結果、残存リスク、未実施項目を作業報告へ残し、完成判定を再現可能にする。 |

> **注記**: 上表「自律ループ」「承認が必要な境界」の2行が示す区分（安全な反復の自動許可／
> 破壊的操作の明示承認）の中核部分は、既に`AGENTS.md`§3「Autonomy and completion
> boundary」で確定運用されている。本節は外部参考資料としての位置づけの説明であり、
> 新規提案ではない。

## AI開発Gate（実装開始前/レビュー時）

- この指示は常設である必要があるか。タスク固有ならtask prompt/referenceに
  移せないか。
- 資料を読む条件が明確か。「毎回全部読む」になっていないか。
- Skillのtriggerは狭く、他のSkillと競合・重複していないか。
- 安全な反復は止めずに進められ、不可逆な境界だけが明示的に止まるか。
- 完了条件に実行・検査・修正・再テストが必要な範囲まで書かれているか。
- モデルが更新されても合理的な環境事実/不変条件なのか、旧モデルの癖への
  対症療法なのか。

## 既存の運用原則との統合

「AIは実装・検証を高速化するが、ゲームループ・経済モデル・リスク/リターン・
プレイヤー体験・優先順位・最終評価は人間が主導する」という原則は維持する。
この追補は、その実装AIを過剰な常設指示で縛らず、必要な境界と完成条件だけを
高精度に渡すための開発環境設計に関する参考論点である。

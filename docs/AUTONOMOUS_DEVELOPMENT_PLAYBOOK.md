# 自動開発プレイブック

このファイルは、「次の開発作業を進めて」という指示を受けたときに
必ず最初から最後まで従う手順書です。過去の開発で実際に起きた事故
(未接続ファイルの放置、循環依存によるスタックオーバーフロー、
pushしていないのに完了報告、間違ったPRのクローズなど)を踏まえて
います。

## ステップ0: 環境確認(必ず最初に行う)

1. git clone と npm test がこの環境で実行できるか確認する。
   できない場合は、GitHubコネクタでの個別ファイル読み書きに
   切り替える(後述の「コネクタのみモード」を参照)。
2. 実行できるなら、main ブランチのHEADコミットを確認する。
3. docs/DEVELOPMENT_ROADMAP.md と docs/gameplay-systems-roadmap.md
   を読み、要約する。
4. 以下を実行し、出力が空であることを確認する(空でなければ、
   実装を始める前にその旨を報告し、先に未接続ファイルを直すか
   指示を仰ぐ):
   ls js/*.js | sed 's#js/##' | while read f; do grep -qF "\"./js/$f\"" index.html || echo "未接続: $f"; done
5. npm test を実行し、現在全テストが通っていることを確認する。
   通っていない場合、新規実装より先にその原因を報告する。

## ステップ1: 次の実装対象を選ぶ

1. ロードマップの中で未実装の項目を、js/配下の既存ファイルと
   照らし合わせて特定する。
2. 1つのPhase・1つの機能だけを選ぶ。複数のPhaseや複数の大きな
   画面を同時に着手しない。
3. 選んだ理由、既存モジュールとの重複がないことの確認結果を報告する。

## ステップ2: 設計時に必ず守るルール

1. 新モジュールの依存方向は一方向にする。「Aの後にBが必要」
   という関係を追加するときは、依存関係を書き出し、最後の1本が
   最初の1本に戻っていないか(循環していないか)手動で確認する。
2. データ→計算→UI→保存→テストを一体で実装する。表示だけ追加して
   計算と連動しない状態を作らない。
3. 旧セーブに安全な初期値を追加する形にする。既存フィールドの
   構造・意味を変更しない。
4. SAVE_KEY=capitalism_tycoon_web_v1 を変更しない。
5. 決定論を保つ(Math.random、Date.now を使わない)。
6. 履歴を持つ配列には上限を設ける。
7. iPhone Safariでの操作性(ボタン高さ44px以上、横スクロール
   なし、1画面に情報を詰め込みすぎない)を守る。

## ステップ3: index.htmlへの接続(最重要)

過去に105本のファイルが未接続のまま放置される事故が起きています。
これを二度と起こさないため、以下を厳守してください。

1. 新しいJSファイルを作ったら、**同じ作業の中で**必ず index.html の
   <script>タグにも追加する。ファイルを作って終わり、次のタスクで
   接続、という進め方は禁止。
2. index.html が1行の巨大なファイルで、GitHubコネクタが部分編集
   ではなく全文置換しか受け付けない場合:
   - 安全に全文を扱える自信がなければ、無理に自分で編集しようと
     せず、新規ファイルの内容と「どの既存scriptタグの直後に
     追加すればよいか」を人間に報告し、判断を仰ぐこと。
   - 中途半端な状態(新規JSファイルだけ存在してindex.htmlに
     未接続)のままコミット・pushしない。
3. 接続後、必ずステップ0-4のコマンドを再実行し、出力が空である
   ことを確認する。

## ステップ4: テストの落とし穴

1. vm.runInNewContext / vm.runInContext を使うテストで、
   assert.deepEqual(sandboxの配列やオブジェクト, リテラル) を
   書くと、別レルム扱いで失敗することがある。この場合は
   assert.equal(対象.length, 期待値) のように構造の一部だけを
   比較する形に直す。
2. 全モジュール読み込みが重くなっている場合、まず
   --max-old-space-size を増やして再実行し、それでも失敗するなら
   ロジックの問題として調査する。「環境の問題です」で済ませない。

## ステップ5: コミット・push・完了報告のルール(最重要)

1. git push が実際に成功したことを、以下のいずれかで確認して
   から「pushしました」と報告する:
   - git ls-remote origin <ブランチ名> の出力に自分のコミット
     ハッシュが含まれることを確認する
   - コネクタしか使えない場合は、コミット後にファイルを
     再読み込みし、変更が反映されていることを確認する
2. push・コミットができなかった場合は、正直に「できませんでした」
   と報告する。「コミットは完了しました」のような、pushの成否を
   曖昧にする表現は使わない。
3. npm test の全出力を、要約せずそのまま貼る。失敗があれば
   失敗内容も隠さず貼る。
4. 実行できなかったコマンド、確認できなかった項目は、全て正直に
   リストアップする。「〜のはずです」という推測での完了報告は
   禁止。

## ステップ6: PRの作成・マージ

1. 1つの機能につき1つのPRを作る。作業ブランチ名は分かりやすく
   Phase名・機能名を含める。
2. PRを作成する前に、対象ブランチが正しいか(mainではなく、
   意図した作業ブランチか)を必ず確認する。
3. 以下の**全て**を満たした場合のみ、自分でPRをマージしてよい:
   - npm test の全出力を実際に確認し、全テストが成功している
   - 未接続ファイルチェックの出力が空である
   - 新規追加したテストが全て成功している
   - PRのdiffが、選んだ1機能の範囲に収まっている(無関係な
     ファイルを変更していない)
   - mergeable: true であることをGitHub側の情報で確認している
4. 上記のいずれか1つでも確認できない場合は、マージせずに
   その旨を報告し、人間の判断を待つ。
5. PRをクローズ・マージする際は、対象のPR番号を復唱してから
   操作する(番号の取り違えを防ぐため)。
6. PRの差分と無関係で、base SHAと同一コードでも再現すると合理的に
   確認できる既存失敗は、以下を全て満たす場合に限り「既存baseline
   failure」としてマージ判断から除外できる。
   - PRの変更ファイルと失敗テストの対象領域が明確に無関係
   - PR固有の対象CIは成功している
   - 失敗内容をログで記録する
   - 既存失敗を修正する別IssueまたはPRを別途作る
   - 新規失敗や悪化がないことを確認する
   - 人間が例外適用を承認する(この規定は自動適用してはならない)

## ステップ7: 完了後、次に進む

1つの機能が完了・マージされたら、「次の開発作業を進めて」と
指示された次回のセッションのために、docs/DEVELOPMENT_ROADMAP.md
または docs/gameplay-systems-roadmap.md の該当箇所に、実装済みで
ある旨を追記してください(既存の記述スタイルに合わせること)。

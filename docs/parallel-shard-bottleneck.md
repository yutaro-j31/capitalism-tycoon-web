# Offline shard bottleneck observation (H/I/K)

The read-only command `node scripts/parallel-shard-bottleneck.cjs TIMING_SUMMARY.json` accepts the **JSON output** of `node scripts/parallel-shard-ci-timing.cjs RUN.json JOBS.json AS_OF_ISO`. Use the complete GitHub run/jobs snapshot (all pages), the exact run attempt, and a retained observation time when producing that upstream summary. The upstream analyzer validates pagination, chronology and job identity. Do not feed raw run/jobs JSON directly to this second-stage command.

The output distinguishes `topObservedExecution` (successful shard start-to-finish) from `topObservedJobCreationToStart` (reported job creation-to-start). `focusHIK` preserves H/I/K's individual timings, state, missing observations and pending age. A job created late after a concurrency hold can have a short creation-to-start delay; inspect the upstream run-creation-to-job-creation metric separately. `runCreationToFirstObservedJobCreationSeconds` records the first observed job of any type; `canonicalShardCreationDelaySeconds` separately gives the observed min/max delay before the twelve canonical shard jobs were created, with a sample count and nulls when absent. `runCreationToAggregateCompletionSeconds` is an optional completed aggregate duration. These are observed API timestamps, **not proof of a concurrency-group wait or a runner-capacity limit**. The top lists include **only observed successful shards with non-null metrics**, with up to three entries and deterministic shard-letter tie breaks. An in-progress, cancelled, failed, skipped or missing shard never enters a success ranking.

`lastObservedSuccessfulShards` is populated only for a completed successful workflow with all twelve canonical shards successful, known completion timestamps, an explicitly successful aggregate, no pending jobs and `completedRunHasPendingJobs=false`. Missing or inconsistent aggregate/pending-child metadata leaves the complete-snapshot flag false and the last-finisher field null; individual shard observations and success rankings remain available. It is the observed last finishing shard (ties retained), **not** a causal critical path or a claim that shortening it will reduce total workflow duration. For partial/cancelled/queued runs the field is null, not an invented winner. `runnerQuota=null` and `productionParallelismAuthorized=false` are deliberate: this tool cannot establish account capacity, realized speedup, host comparability, or approval to change parallelism.

This tool reads local JSON only; it does not start workload, fetch APIs, alter GitHub Actions, rerun/cancel workflows, change shard variables or touch Economic Engine/SAVE. Its short synthetic controls are invoked by the existing required timing/overlap self-test chain. J/C production parallelism remains 2; E/K remain serial and Owner-held production changes remain prohibited. Use repeated comparable, independently verified runs before any separate Owner decision on K/H/I production settings.

## Fixed-timing completion model

`fixedTimingCompletionModel` is populated only for the same complete successful snapshot required above. For each shard, `completionSlackSeconds` is the last canonical finish minus that shard's finish. `maximumEndReductionSeconds` is the arithmetic ceiling on moving the **canonical shard end** by shortening only that shard's runtime, while every other shard's start/finish remains fixed. It is `min(selected runtime, max(0, selected finish − latest other finish))`. A non-last or tied-last shard has ceiling zero. A uniquely last shard with unknown runtime has null ceiling; a missing/incomplete/failed/pending snapshot has a null model. A zero-second ceiling under these assumptions is not proof that an optimization has no queue/occupancy benefit.

This is a hypothetical bound, **not measured speedup or a causal workflow critical path**. It lets the selected runtime shrink to zero, keeps queue/admission and other jobs fixed, and does not reschedule the aggregate or noncanonical jobs. It cannot predict the result of actual parallelism, resource contention, earlier runner release, changed workflow concurrency cancellation or a different set of simultaneous runs. `scope=canonical-shard-end-only` and `measuredSpeedup=false` are explicit. No total-workflow improvement or runner quota is inferred.

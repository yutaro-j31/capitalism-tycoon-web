# Capitalism TYCOON 開発ロードマップ

## 全開発で守る方針

- 既存機能を削除しない。
- 既存機能を勝手に簡略化しない。
- `localStorage` の保存キー `capitalism_tycoon_web_v1` を変更しない。
- 既存セーブデータとの互換性を維持する。
- 新規ゲームと旧セーブの両方をテストする。
- GitHub Pagesで動く構成を維持する。
- iPhone Safariでプレイできる状態を維持する。
- 一度に大量のシステムを変更しない。
- 原則として1つの責務ごとにPull Requestを分ける。
- 数値変更には理由とテスト結果を残す。
- 表示だけ追加して計算と連動しない状態を作らない。
- データ、計算、UI、保存、レポートを一体で実装する。
- 新機能は旧セーブに安全な初期値を追加する。
- ゲームバランスと構文検査を別々に検証する。
- テスト用に資金を無限化した長期テストだけでバランスを判断しない。

## Phase 0: 現状監査・構造整理・テスト基盤・セーブ互換性基盤

- 目的: 壊さず開発できる土台を作る。
- 追加するデータ: サンプル旧セーブ、テストフィクスチャ、保存スキーマ一覧。
- 変更する既存処理: 原則なし。テスト追加後に `normalize` の責務整理を検討。
- 新しい画面: なし。
- セーブ影響: なし。将来マイグレーション設計のみ。
- マイグレーション: 未実装。設計文書化。
- テスト: 構文、HTML、保存往復、旧セーブ読込、長期週送り、主要値非NaN検査。
- PR数: 4〜8。
- 依存Phase: なし。
- リスク: 現状コードの巨大さにより監査漏れが起きる。
- 完成条件: docs整備、テスト基盤、旧セーブfixture、リファクタ手順が揃う。

## Phase 1: 市場需要・顧客セグメント・商品別収益

- 目的: 店舗/商品ごとの売上理由を見える化し、市場シェア争いの土台を作る。
- 追加するデータ: 商品/サービス単位の市場規模、顧客セグメント、価格弾力性、品質/ブランド評価、チャネル別需要。
- 変更する既存処理: 店舗売上計算、`customerSegmentsByBusinessID`, `marketShareByBusinessID`, レポート。
- 新しい画面: 市場分析、商品別P/L、売上変動理由。
- セーブ影響: 業種別市場状態、商品別KPIを追加。
- マイグレーション: 既存 `businesses` から安全な初期市場を生成。
- テスト: 同一旧セーブで初期値補完、価格変更で需要が変わる、売上理由の合計整合。
- PR数: 5〜8。
- 依存Phase: Phase 0。
- リスク: 既存店舗売上バランスを壊す。
- 完成条件: 売上=客数×単価が説明可能になり、UI/保存/計算が連動する。

## Phase 2: 会計三表・運転資本・黒字倒産

- 目的: 資本主義/会計を学べる経営シミュレーションの中核を作る。
- 追加するデータ: 損益計算書、貸借対照表、キャッシュフロー、売掛金、買掛金、在庫、固定資産、減価償却、運転資本。
- 変更する既存処理: `reports`, 店舗/不動産/投資/借入/税/配当の記録方法。
- 新しい画面: 財務諸表、資金繰り、運転資本ダッシュボード。
- セーブ影響: 会計帳簿、勘定残高、未収未払を追加。
- マイグレーション: 旧セーブの現金/負債/資産から簡易BSを初期生成。
- テスト: 三表整合、現金増減一致、減価償却、黒字倒産判定。
- PR数: 8〜12。
- 依存Phase: Phase 1推奨、Phase 0必須。
- リスク: 既存の現金直接増減が多数あり、二重計上しやすい。
- 完成条件: 週次の現金増減がCFで説明でき、PL/BS/CFが保存される。

## Phase 3: 仕入先・原材料・生産能力・物流・在庫

- 目的: 売上成長に対して供給制約とオペレーション判断を導入する。
- 追加するデータ: 原材料、仕入先別価格/品質/リードタイム、生産能力、物流能力、設備稼働率、不良率。
- 変更する既存処理: `updateSupplyChainWeekly`, 店舗売上、原価、在庫、垂直統合。
- 新しい画面: サプライチェーン管理、在庫/欠品、設備稼働率。
- セーブ影響: SKU/原材料在庫、仕入契約、設備能力。
- マイグレーション: 既存業種ごとに標準原材料と安全在庫を生成。
- テスト: 在庫不足で売上減、仕入遅延、設備投資後の能力増、負在庫防止。
- PR数: 6〜10。
- 依存Phase: Phase 1, Phase 2。
- リスク: 複雑化でスマホUIが重くなる。
- 完成条件: 欠品/物流/能力が売上と粗利に説明可能に反映される。

## Phase 4: 人材能力・工程・疲労・組織ボトルネック

- 目的: 部門人数だけでなく、能力と組織設計が成長制約になるようにする。
- 追加するデータ: 職種、社員能力、処理能力、疲労、モチベーション、管理職、プロジェクト工程。
- 変更する既存処理: `departmentStaff`, `employeeSatisfaction`, キーパーソン、部門効果。
- 新しい画面: 組織図、人材配置、採用市場、プロジェクト工程。
- セーブ影響: 社員/職種/工程配列を追加。
- マイグレーション: 既存部門人数から代表社員または集約社員グループを生成。
- テスト: 採用/退職、疲労上昇、管理職不足、工程遅延。
- PR数: 8〜12。
- 依存Phase: Phase 0, Phase 1。
- リスク: 個別社員を増やすとセーブが肥大化する。
- 完成条件: 組織ボトルネックが売上/開発/品質に連動する。

## Phase 5: 競合企業AI

- 目的: 価格、広告、人材、R&D、市場参入撤退で競争環境を作る。
- 追加するデータ: 競合企業の戦略、財務、商品、店舗、市場シェア、倒産/再建状態。
- 変更する既存処理: `competitors`, `competitorStates`, 需要計算、市場シェア。
- 新しい画面: 競合分析、競争イベント、価格/広告戦略比較。
- セーブ影響: 競合別状態を詳細化。
- マイグレーション: 既存競合から簡易財務/戦略を生成。
- テスト: 競合値下げでシェア変化、倒産、撤退、再建。
- PR数: 8〜14。
- 依存Phase: Phase 1。
- リスク: AI処理が重くなる。ランダム性でテストが不安定。
- 完成条件: 競合行動がプレイヤー売上に説明可能に影響する。

## Phase 6: 社内資本配分・事業部別ROIC・子会社独立経営

- 目的: コングロマリット経営を成立させる。
- 追加するデータ: 事業部、投下資本、ROIC、子会社CEO、親子会社シナジー、事業売却候補。
- 変更する既存処理: `subsidiaries`, `maSubsidiaries`, 店舗/商品/不動産の所属管理。
- 新しい画面: 事業ポートフォリオ、資本配分会議、子会社管理。
- セーブ影響: 事業部ID、資本配分履歴、子会社KPI。
- マイグレーション: 既存店舗/商品/子会社を初期事業部に割当。
- テスト: ROIC計算、子会社配当、事業売却、子会社IPO。
- PR数: 8〜12。
- 依存Phase: Phase 2。
- リスク: 既存会社価値計算との二重計上。
- 完成条件: 事業別投資判断と売却/IPOが財務に整合する。

## Phase 7: M&A高度化

- 目的: 買収を資本政策・PMI・のれんまで含む本格システムにする。
- 追加するデータ: 候補探索、企業価値評価、DD項目、交渉、資金調達、PMI、のれん、減損、人材流出、文化衝突。
- 変更する既存処理: `generateMATargets`, `acquireTarget`, `goodwillRecords`, `maSubsidiaries`。
- 新しい画面: M&Aパイプライン、DDレポート、PMI計画。
- セーブ影響: DD結果、交渉履歴、PMIタスク、のれん償却/減損履歴。
- マイグレーション: 既存M&A子会社に簡易PMI完了状態を付与。
- テスト: 買収価格、資金調達、減損、PMI失敗、人材流出。
- PR数: 10〜16。
- 依存Phase: Phase 2, Phase 6。
- リスク: 会計とゲームバランスが複雑。
- 完成条件: 買収後の価値創造/破壊がレポートで説明できる。

## Phase 8: 企業危機・再建

- 目的: 経営不振企業の再建と倒産回避をゲーム性にする。
- 追加するデータ: 13週間資金繰り、債務再編、スポンサー、事業再生ファンド、リストラ計画、金融機関交渉。
- 変更する既存処理: ゲームオーバー、借入、返済、会社売却、M&A。
- 新しい画面: 危機管理室、資金繰り表、再建計画。
- セーブ影響: 危機状態、交渉履歴、再建KPI。
- マイグレーション: 現金/債務から危機レベルを計算。
- テスト: 資金ショート、返済猶予、スポンサー増資、事業売却。
- PR数: 8〜12。
- 依存Phase: Phase 2。
- リスク: 難易度が急上昇し離脱を招く。
- 完成条件: 倒産前に複数の再建手段が機能する。

## Phase 9: チュートリアル・学習・演出・品質改善

- 目的: 学習コンテンツと販売向け品質を整える。
- 追加するデータ: チュートリアル進捗、用語解説、学習カード、イベント演出、効果音設定、アクセシビリティ設定。
- 変更する既存処理: UI、設定、ミッション、イベント表示。
- 新しい画面: チュートリアル、用語集、学習ログ、アクセシビリティ設定。
- セーブ影響: チュートリアル進捗、既読ヘルプ、音量/表示設定。
- マイグレーション: 既存セーブはチュートリアル任意表示にする。
- テスト: 初回導線、旧セーブで邪魔しない、iPhone Safari、スクリーンリーダー、効果音ON/OFF。
- PR数: 10〜18。
- 依存Phase: Phase 0。一部は並行可能。
- リスク: 表示だけ増えて計算と乖離する。
- 完成条件: 新規プレイヤーが段階的に学び、スマホで最後まで遊べる。

## v2.1で最初に実装すべきシステム

Phase 0完了後、v2.1の最初は Phase 1 の「商品/サービス別売上分解」と「売上変動理由」を推奨する。理由:

- 現在すでに `businesses`, `stores`, `customerSegmentsByBusinessID`, `marketShareByBusinessID` が存在する。
- 会計三表や競合AIの前提になる。
- プレイヤーが価格、品質、ブランド投資の意味を理解しやすくなる。
- 保存スキーマへの追加が比較的安全。

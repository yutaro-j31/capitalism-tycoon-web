## 0. 結論

4シリーズを横断すると、優れた経営シミュレーションに必要なのは「機能の数」ではない。
中心にあるのは、プレイヤーが状況を観察し、意思決定し、時間を進め、結果を理解し、
次の判断につなげる循環である。

```
OBSERVE(観察) → DECIDE(意思決定) → COMMIT(時間進行) → SIMULATE(世界更新)
→ EXPLAIN(因果説明) → REPEAT(次の判断)
```

このループが深ければ、機能数が少なくてもゲームは深くなる。逆に、機能が多くても
各機能がこの循環に接続していなければ、巨大なメニュー集になってしまう。

**シミュレーションの深さは「操作量」ではなく「意思決定の因果関係」で作る。**

設計上の中心命題:
- 会社の成長に伴って、プレイヤーの仕事そのものを変える。
- 複雑さは操作回数ではなく、選択肢同士のトレードオフから生む。
- 結果を出すだけでなく、なぜそうなったかを説明する。
- 長期プレイ、セーブ互換、性能、詰み状態を最初から設計対象にする。
- AIで実装速度が上がっても、ゲームルールとバランスの設計は人間が主導する。

## 1. 4シリーズに共通する設計

| 共通設計 | 実際に行われていること | 設計上の意味 |
|---|---|---|
| 明確な時間単位 | 日・週・ターン・月・シーズン | 判断と結果を区切る |
| プレイヤーは管理者 | 直接操作より判断が中心 | 経営ゲームとしての純度を保つ |
| 複数の成長手段 | 投資・採用・買収・研究・補強 | 一本道を防ぐ |
| 資源制約 | 現金・人員・時間・枠・在庫 | トレードオフを生む |
| 遅延効果 | 投資しても即時に全成果が出ない | 将来予測をゲームにする |
| 不確実性 | イベント・競争・交渉・成長 | 同じ手順の反復を防ぐ |
| 中長期目標 | IPO・タイクーン・優勝など | 長期プレイを支える |
| 自動処理 | 試合・市場・競合・売上計算 | プレイヤーを判断に集中させる |
| 数値フィードバック | 財務・順位・市場シェア・能力 | 結果を理解させる |
| プレイテスト | 実プレイ + 自動シミュレーション | 設計の穴を検出する |

優れた経営ゲームでは「Aが正解、Bが不正解」ではなく、AにはAのリターンとリスク、
BにはBのリターンとリスクがある。

## 2. 12の設計原則

1. **ゲームの最小単位を「意思決定→時間進行→結果」にする**
   機能追加のたびに、このループのどこへ接続するかを明確にする。接続できない
   機能は慎重に扱う。「店舗を見る→価格・営業時間・投資を決める→週を進める→
   売上・客数・競合・現金が変化する」が基本単位になる。

2. **成長するとプレイヤーの仕事そのものを変える**
   会社が拡大しても1店舗目と同じ操作を繰り返させない。店主から複数店舗オーナー、
   CEO、グループCEO、資本家へと意思決定の抽象度を上げる。

3. **便利さとゲーム性を区別する**
   経営上の摩擦は残してよいが、UI上の摩擦は消す。管理負荷は委任・採用・組織
   設計の理由にできる一方、無意味なタップ数や深いメニューはゲーム性ではない。

4. **一つの最適解を作らない**
   価格、品質、広告、立地、設備、人材、借入、M&Aなどに複数の勝ち筋を作る。
   全戦略を同じ強さにする必要はないが、単一のdominant strategyは避ける。

5. **投資には時間差を持たせる**
   広告・設備・人材・ブランド・IT・R&Dは即時100%効果にしない。資金が先に減り、
   成果が遅れて出ることで資金繰りと成長投資の緊張関係が生まれる。

6. **不確実性はプレイヤーの選択と結びつける**
   完全な運ではなく、準備状態・契約・財務余力・組織力などでショックの影響が
   変わる設計にする。決定論を維持する場合はseed由来の再現可能な不確実性が適する。

7. **結果だけでなく「なぜ」を表示する**
   売上や利益の変化を単なる数字で終わらせない。価格変更、客数、競合行動、
   人件費、需要変化などの寄与を説明し、プレイヤーがゲームのルールを学べる
   ようにする。

8. **詰ませる状態には事前ガードを置く**
   現金不足・人員不足・契約不能・進行不能などのsoft-lockを自動検出する。
   詰みになる前に救済策、警告、強制的な最低限の選択肢を用意する。

9. **機能追加で操作回数を増やさない**
   システムが深くなっても、タップ数は可能なら減らす。progressive disclosure、
   既定値、委任、まとめ操作、方針設定を使う。

10. **長期プレイを最初からデータ設計に入れる**
    現在状態と履歴を分離し、全履歴を常時ロードしない。必要時ロード、集約、
    アーカイブ、上限管理を設計する。100年プレイを想定するならstate sizeも
    KPIにする。

11. **セーブをゲーム機能として扱う**
    saveVersion、migration、atomic save、バックアップ世代、破損検知をゲーム
    ロジックと同格に扱う。長期ゲームではセーブ破損の損失が大きい。

12. **AIには実装を任せ、人間はゲームルールを決める**
    AIは実装・テスト・リファクタリングを高速化できるが、経済モデル、破産ライン、
    投資ROI、意思決定の面白さを自動的に保証しない。人間は設計と評価に集中する。

## 3. 失敗した設計と反面教師

| 失敗 | 典型例 | 原因 | 設計原則 |
|---|---|---|---|
| 結果が予想できすぎる | 交渉・訴訟が毎回同じ | 決定論が強すぎる | 制御された不確実性 |
| 特定戦略が強すぎる | 投資極振り等が常勝 | ROIの偏り | 多戦略シミュレーション |
| 初期状態がおかしい | 極端な勝敗・数値 | state初期化の不正 | E2E初期state検証 |
| プレイヤーが詰む | 人数・現金不足で進行不能 | 状態遷移の抜け | soft-lock検査 |
| 機能追加でUI悪化 | 1タップが多段操作へ | 概念をそのまま操作にした | progressive disclosure |
| 長期ほど重くなる | 履歴を全件ロード | state/history未分離 | 集約・遅延ロード |
| セーブ消失 | 破損・上書き事故 | 保存設計不足 | atomic save + backup |
| 因果関係が分からない | 結果だけ表示 | 説明不足 | explainability |
| 追加機能が連鎖破壊 | 一変更で複数機能が壊れる | 依存関係が強すぎる | 境界を切った設計 |
| 現実を再現しすぎる | 入力項目ばかり増える | 複雑さをそのまま実装 | 意思決定を抽象化 |

重要なのは、計算式単体が正しいことではない。state生成→意思決定→simulation→
state更新まで通したEnd-to-End検証が必要である。

## 4. 資本主義ポケット TYCOONに取り入れるべき中核構造

既存の「都市を見る→物件を見る→賃貸契約→店舗を出す→価格・営業時間を決める→
週を進める」という核を、以下の6段階ループとして明示する。

| フェーズ | 内容 |
|---|---|
| OBSERVE | 都市/競合/需要/店舗状態/現金/市場状況 |
| DECIDE | 価格/営業時間/商品/人員/広告/設備/物件/資金調達 |
| COMMIT | 「次の週へ」などの明示的な時間進行 |
| SIMULATE | 需要/競合行動/客数/売上/原価/人件費/固定費/評判/イベント |
| EXPLAIN | 売上変化/客数変化/利益率変化/競合影響/資金圧迫の理由 |
| REPEAT | 得られた情報を次の意思決定に反映 |

この循環をゲームエンジンの心臓とみなす。新機能は必ずこのどこかへ接続する。

## 5. 経営者レイヤーの進化

最も重要な進化は「機能を横に増やすこと」ではなく、会社の成長に応じてプレイヤーの
役割を上位レイヤーへ移すことである。

| 段階 | プレイヤーの役割 | 主な意思決定 |
|---|---|---|
| Stage 1 | 店主 | 価格・営業時間・商品 |
| Stage 2 | 複数店舗オーナー | 出店・店長・広告 |
| Stage 3 | CEO | 人事・商品開発・資本配分 |
| Stage 4 | グループCEO | 新規事業・M&A・借入 |
| Stage 5 | 上場企業経営者 | IR・株主・配当・資本政策 |
| Stage 6 | 資本家 | PE・VC・株式・不動産 |
| Stage 7 | コングロマリット | ポートフォリオ全体の資本配分 |

**Policy化の原則**: 後半になっても店舗単位の価格を毎週手入力させない。代わりに
「価格戦略: プレミアム」「利益率目標: 18%」「店長裁量: 高」などのpolicyを設定し、
現場は自動運営させる。成長を数字ではなく操作の変化として感じさせる。

## 6. イベントと不確実性の設計

ランダムイベントは単なるテキスト抽選では弱い。外部ショックの影響が、それまでの
経営判断によって変化する必要がある。

| 例 | 事前状態 | 結果 |
|---|---|---|
| 原材料高騰 | 安い仕入先しかない | 粗利-8% |
| 原材料高騰 | 長期仕入契約済み | 粗利-2% |
| 原材料高騰 | 高級業態で価格弾力性が低い | 値上げ吸収が可能 |

理想は、プレイヤーが「運が悪かった」ではなく「前に仕入契約をしておけばよかった」
と考える状態である。

## 8. ゲームバランス検証

人間のテストプレイだけでは、dominant strategyや長期破綻を見逃しやすい。複数の
戦略Botを用意して100〜1,000ゲーム単位で自動実行する。

想定Bot: 価格重視 / 低価格大量販売 / 高価格高利益 / 出店拡大型 / 現金保守型 /
借入レバレッジ型 / 広告型 / 設備投資型 / 人材型 / M&A型 / 無策型

| 指標 | 意味 |
|---|---|
| 10年生存率 | 詰み・難易度 |
| 倒産率 | リスク |
| 店舗数中央値 | 成長速度 |
| 営業利益率 | 経営効率 |
| 企業価値 | 長期成果 |
| 最大ドローダウン | 危機の深さ |
| 戦略別勝率 | dominant strategy検出 |
| 無操作時の結果 | ベースライン |
| 100年state size | 長期性能 |
| NaN/Infinity | 計算破壊 |

目標は「全戦略を同じ強さにする」ことではない。高リスク高リターン、低成長だが
高生存率、序盤に強いが後半に弱い、といった戦略の性格を作る。

## 9. モバイルUI原則

モバイルでは、システムの複雑さを画面遷移やタップ数に変換しない。情報密度は
高くてもよいが、操作構造は単純であるべき。

- 店舗画面: この店は儲かっているか？
- 物件画面: ここに出店すべきか？
- 財務画面: 今どれだけリスクを取れるか？
- M&A画面: この会社をこの価格で買うべきか？

**1画面=1つの経営質問。視覚情報密度は高く、操作構造は単純に。**

## 10. AI開発時代の開発原則

AIによってコードを書く速度は大幅に上がる。しかし、面白い経済モデル、適切な
破産ライン、投資ROI、意思決定のトレードオフを決める難しさは消えない。

| AIに任せる領域 | 人間が主導する領域 |
|---|---|
| 実装/リファクタリング/focused test/自動検証/静的解析/仕様に沿った修正 | ゲームループ/経済モデル/リスク・リターン/プレイヤー体験/優先順位/最終評価 |

実装速度をゲームの完成度と勘違いしない。100個の孤立した機能より、10個の
相互作用するシステムの方が深い。

## 11. 設計憲法

今後の仕様追加は、次のgateを通過したものだけを実装候補とする。

- この機能は、新しい意思決定を生むか。
- 既存の意思決定とのトレードオフを生むか。
- OBSERVE/DECIDE/COMMIT/SIMULATE/EXPLAINのどこに接続するか明確か。
- プレイヤーの操作回数を不必要に増やしていないか。
- 結果の理由を説明できるか。
- 長期プレイでデータ量・性能・セーブに問題を起こさないか。
- 一つの最適解を固定化しないか。
- 会社成長後に委任・自動化・policy化できるか。
- 決定論、会計整合、セーブ互換と矛盾しないか。
- その機能がなくても成立するなら、本当に今追加すべきか。

**成長によって操作が増えるのではなく、意思決定のレベルが上がる。**

## 12. 実装チェックリスト

機能実装前・レビュー時・長期テスト時に使用する。

| 領域 | 確認項目 |
|---|---|
| Game Loop | 新機能が意思決定→時間進行→結果へ接続している |
| Trade-off | 利益とコスト、成長とリスクなど明確なトレードオフがある |
| Explainability | 結果変化の主要因をUIで説明できる |
| Mobile UX | 主要操作が少ないタップで完結し、1画面の目的が明確 |
| Delegation | 規模拡大後に自動化・委任・方針設定へ移行できる |
| Balance | 複数Botでdominant strategyを検査している |
| Soft-lock | 資金・人員・契約等の詰み状態を検査している |
| Save | saveVersion/migration/atomicity/fallbackを確認 |
| Performance | 10年/30年/100年でstate size・処理時間を計測 |
| Determinism | 同save+同操作で同結果を維持 |
| Accounting | 会社現金・個人現金・台帳の二重計上がない |
| Regression | 初期stateからE2Eで主要導線を通す |

## 13. 最終的に目指すゲーム像

目標は「店舗経営ゲーム+株+M&A+不動産+PE+VC」という機能集合ではない。小さな
1店舗を経営する人物が、時間とともに経営者として成長し、最後には企業ではなく
資本そのものを配分する存在になるゲームである。

| 時期 | 意思決定の例 |
|---|---|
| 序盤 | 「この店の価格を980円にするか1,080円にするか」 |
| 中盤 | 「東京に10店舗出すか、別地域へ進出するか」 |
| 後半 | 「30億円を既存事業、M&A、配当、VCのどこへ配分するか」 |
| 終盤 | 「どの企業を所有し、誰に経営させ、どこへ資本を移すか」 |

同じゲームの中で、意思決定の抽象度が徐々に上がっていく。これを成長体験
そのものにする。

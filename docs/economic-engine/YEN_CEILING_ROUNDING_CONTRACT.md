# Whole-Yen Ceiling Rounding Contract (Phase 0 §5 vNext)

**Status: APPROVED — merged by the Owner in #1074 (2026-10-22).**
**Owner decision (2026-10-22):** every in-game monetary amount is settled in whole yen. Any fraction of a yen is **rounded up** (切り上げ). Old saves do not need to stay compatible (Owner decision of the same day; `AGENTS.md` and `CLAUDE.md` were updated by #1071). Saves created before R9 are **outside the whole-yen guarantee**; see §1.1.
**Supersedes:** the ¥0.01 posting quantum in `PHASE_0_CONTRACTS.md` §5.1/§5.3 and ECO-019, slice by slice, as recorded in §8 below.

This document is written so that **any agent** (Claude Code, Codex/ChatGPT, or another) can pick up the work at any slice. If you are resuming this work, read §9 first.

## 1. Scope

In scope: every monetary amount that the game **settles or posts**, for every party:

- company cash, debt, ledger rows (`finance.event` amounts and their `cashEffect` / `profitEffect` / `assetEffect` / `liabilityEffect`), loan rows, fixed-asset and property book values;
- personal cash, debt and personal holdings' settled amounts;
- competitor, PE-rival and other NPC money (`competitorStates` cash/debt, fund balances).

Out of scope (keep their current precision; do **not** round them):

- rates, ratios, ownership/voting fractions, FX rates, weights, scores, probabilities;
- share/security quantities (already integer by their own contracts);
- per-share prices, valuations, market values, forecasts and other estimates **until** they are settled or posted. When one of them is posted, the posted amount is rounded by this contract.
- UI formatting (display already shows whole yen; an integer amount displays the same).

### 1.1 Saves created before R9

The whole-yen guarantee and the strict checks of §6 apply to **games started after R9**. A save created earlier is excluded from them, but it still loads and plays:

- Every persisted monetary value keeps its stored fraction: cash, debt, `finance.fixedAssets[].bookValue`, loan rows, property and mortgage balances, deposits, fund and holding values. Nothing is normalised on load, because rewriting a stored amount would create or destroy money. Nothing is rejected, because rejecting saves is a save-semantics change that would need its own Owner decision.
- A migrated writer that operates on such a value uses it as stored. A payment capped by a fractional balance posts the capped amount (§3.5). A disposal of a fractional book value posts the fractional `assetEffect` and `profitEffect` it implies. State and ledger agree to within the existing legacy validation tolerances (Phase 0 §5.5): `finance.event`'s ¥0.01 normalisation may still round a sub-cent legacy operand such as ¥10.504 to ¥10.50 in the ledger. No stricter agreement is promised for these saves. §3.2's "already whole" premise does not hold for these operands, and nothing is rounded again to hide that.
- The existing accounting checks (`finance.validate`, the debt rollforward) still apply to such saves; only the whole-yen checks do not. The Owner starts device testing from a new game (2026-10-22), so no further handling is planned.

## 2. The rounding function

One shared implementation lives in `js/economic-operation.js` (it loads third, before every economic writer) and is exported as `economicOperation.ceilYen`:

```text
ceilYen(x):
  require typeof x === 'number' and finite                 (TypeError otherwise)
  require |x·100| <= MAX_SAFE_INTEGER                         (RangeError otherwise; the same envelope as roundMoney)
  k   = Math.round(x)
  tol = min(0.005, max(1e-9, |x| · 4 · Number.EPSILON))     (about four ULPs at x's magnitude, never more than ¥0.005)
  y   = |x − k| <= tol ? k : sign(x) · ceil(|x|)              (float noise snaps to k; every real fraction rounds the magnitude up)
  return y === 0 ? 0 : y                                     (never return -0)
```

Consequences, which are intended:

- `ceilYen(12.3) = 13`, `ceilYen(-12.3) = -13`: a payment and a receipt each grow by the fraction. Do **not** use bare `Math.ceil`; for a negative amount it moves toward zero (`Math.ceil(-12.3) = -12`).
- `ceilYen(1200.0000000002) = 1200` and `ceilYen((0.1+0.2)*10) = 3`: a difference within float precision is noise, not a fraction. Any larger fraction rounds up: `ceilYen(12.004) = 13`, `ceilYen(1200.004) = 1201`, `ceilYen(0.1+0.2) = 1`. Do **not** normalise to ¥0.01 first; that would drop real sub-¥0.01 fractions.
- The absolute floor of 1e-9 is the contract's minimum monetary quantum: a fraction **at or below** ¥0.000000001 is treated as noise, because the comparison is `<=` (`ceilYen(1e-9) = 0`, `ceilYen(1.0000000005) = 1`, `ceilYen(5e-10) = 0`). The 1e-9 floor governs only below |x| ≈ ¥1.1·10⁶; above that the relative term is larger. In general a fraction rounds up only when it exceeds the **full computed tolerance**: `ceilYen(1.000000002) = 2`, but `ceilYen(1e9 + 1e-7) = 1e9`, because the tolerance at 1e9 is about 8.9e-7. No game formula produces a meaningful amount that small.
- `ceilYen(12) = 12`. The function is idempotent: rounding an already rounded amount does nothing.
- The tolerance is about four ULPs of x, so it absorbs the noise of a few arithmetic steps (for example `11000000 * 1.1`). It is capped at ¥0.005, so a fraction of ¥0.01 or more always rounds up anywhere in the envelope: `ceilYen(1e12 + 0.01) = 1e12 + 1`, `ceilYen(1e13 + 0.01) = 1e13 + 1`. Below |x| ≈ ¥5.63·10¹² (where `|x|·4·EPSILON = 0.005`) the cap is not reached, and the tolerance is four ULPs or 1e-9, whichever is larger; above it the tolerance is exactly ¥0.005. R0's boundary tests cover both sides of that point.

A writer's **private** helper (for example `const round=v=>Math.round(n(v)*100)/100` in a real-estate module) replaces its body with a call to the shared function, but only when every caller of that helper is in the same slice. It does not keep a private copy of the rule. A helper that also coerces non-finite values (`n(v)`) keeps that coercion before calling `ceilYen`.

**Shared normalisers stay ¥0.01; they are never switched to `ceilYen`.** `finance.js`'s `r`, which `finance.event` applies to the amount and every effect of a ledger row, and `economic-settlement.js`'s use of `roundMoney` serve writers in every slice, and also derive statement and reconciliation figures. If one of them were switched early, a writer that has not migrated yet would write a cent value to state while its ledger row became whole yen. A migrated writer instead calls `ceilYen` itself, **before** it writes state or calls `finance.event`. The ¥0.01 normaliser leaves a whole-yen amount unchanged, so state and ledger agree. The shared normalisers are **never switched to `ceilYen`**, not even at R9. Switching `r` globally would turn a pre-R9 ¥10.5 book-value disposal into an ¥11 ledger effect against a ¥10.5 state change, breaking §1.1. It would also make `finance.validate()`'s fixed-asset checks reject historical fractional data. At R9 the ¥0.01 normalisation in `finance.event` either stays, which is harmless: it is the identity on whole-yen amounts and preserves cent-quantised pre-R9 fractions exactly; a sub-cent legacy operand keeps only the §1.1 tolerance. Or it is removed or bypassed, so that `finance.event` records the amount it is given. Validation, statement and reconciliation arithmetic keeps its own ¥0.01 helper either way. The same rule applies to any other helper with callers in more than one slice.

## 3. Where rounding happens

Rounding happens **once**, at the point where an amount is settled or posted. It does not happen repeatedly in intermediate formulas (unchanged from Phase 0 §5.3).

1. **Compute, round, then write.** A writer computes the amount, rounds it once with `ceilYen`, and uses that **same** value for the state field (`companyCash`, `companyDebt`, `mortgageBalance`, …) and for every effect on the ledger row. Writing an unrounded value to state and a rounded one to the ledger (or the other way round) breaks the balance sheet.
2. **Derived amounts are not rounded again.** A gain = proceeds − book value, a net = gross − fee, or a new balance = old − payment is the difference of two whole-yen amounts, so it is already whole. Do not call `ceilYen` on it, because that hides a component that was not rounded.
3. **Caps keep their cap.** When a balance caps an amount (a payment cannot exceed the balance; depreciation cannot exceed the remaining book value), round first, then cap: `min(ceilYen(x), balance)`. Rounding up never makes a payment exceed what is owed, nor a book value go negative.
4. **Cash limits.** When available cash limits a payment (`min(due, cash)`), round `due` first.
5. **During the migration, balances can still carry fractions.** Until R9, writers that have not migrated yet (and saves created before R9, §1.1) can leave a fraction in `companyCash` or another balance. A migrated writer whose amount is capped by such a balance posts the capped amount **as is**, without rounding up past the balance, and writes that same value to state and ledger. This is one of the two cases where a migrated writer may post a non-whole amount; the other is an operand loaded from a save created before R9 (§1.1). In a game started after R9 neither can occur, because every writer posts whole yen. The runtime guard (§6) therefore checks migrated rows in scenarios that start from whole-yen balances, and from R9 it checks all rows strictly in a new game. It also adds one scenario that loads a fractional pre-R9 save, performs a capped payment and a fractional book-value disposal, and asserts that state and ledger agree and the books validate.

## 4. Splitting one amount into parts

Rounding every part separately makes the parts disagree with the rounded total (12.3 + 87.4 = 99.7 → 100, but 13 + 88 = 101). Rule:

- **Two parts (charge + remainder).** Round the total. Round the *charge* part (interest, fee, tax, commission). If a cap (§3.3–§3.4) lowers the total, apply it to the total first, then cap the charge to that final total: `charge = min(ceilYen(charge), total)`. The other part is `total − charge`. Both parts are then never negative and always sum to the total. Example of a cap: due ¥1.2 with interest ¥1.1 rounds to due ¥2 and interest ¥2. If available cash caps the payment at ¥1, then interest = min(2, 1) = ¥1 and principal = ¥0. Example: due = `ceilYen(99.7) = 100`, interest = `ceilYen(12.3) = 13`, principal = `100 − 13 = 87`.
- **Many recipients (dividends, distributions, allocations, waterfalls).** Round the aggregate with `ceilYen`. Give each recipient `floor` of its exact share. Hand the remaining yen out one at a time by **largest fractional remainder**; break ties by stable entity/security ID, ascending. This fulfils Phase 0 §5.4: the residual is deterministic, attributed to a named recipient, and the parts sum exactly to the total. The shared helper `economicOperation.allocateYen(total, weights, ids)` implements this rule; writers must not invent their own.
- **Per-unit or per-holder rounding.** A family-specific contract may round per unit or per holder instead (for example, a fixed per-share dividend). It must say so explicitly in that family's slice notes in §8.

## 5. What does not change

- `SAVE_KEY`, `saveVersion=9`, determinism, company/personal separation, and the ban on `Math.random()` in simulation paths.
- Legacy validation tolerances in `finance.validate()` (Phase 0 §5.5) stay as they are during the migration. Tightening them is a separate, later PR after slice R9.
- `roundMoney` keeps its current ¥0.01 behaviour, and `tests/economic-operation-contract-test.js` keeps its assertions. `ceilYen` does not call it (§2).

## 6. Determinism, fixtures and tests

- Changing a rounding rule legitimately moves money values, fingerprints and possibly the RNG call count, wherever a branch depends on an amount (for example, "can the company afford X"). A slice may update a fixture such as `tests/fixtures/transaction-baseline-v1.json` **only** under all of these conditions:
  - the PR body explains which values moved and why;
  - the accounting identities (`finance.validate`, the debt rollforward) still hold;
  - no transaction appears or disappears without a stated reason.
- An existing test that asserts a cent value (for example `1234.56`) gets the new whole-yen expected value. This applies the approved contract; it does not weaken the test. Never delete a test, skip it, or widen a tolerance to make it pass.
- **Ratchet guard** (added in slice R0): `tests/yen-ceiling-rounding-guard-test.js` with its baseline `tests/fixtures/yen-ceiling-rounding-baseline.json`. It checks two things:
  - **Lexical ratchet.** The baseline's `pendingFiles` lists the `js/` files that still contain a ¥0.01 rounding pattern (`*100)/100` and its spacing variants). The test fails in two cases:
    - a file **not** in `pendingFiles` contains the pattern. A new or migrated file must not reintroduce cent rounding.
    - a file **in** `pendingFiles` no longer contains it, i.e. the entry is stale. So each slice must remove its files from the list.

    The pattern can also round a non-monetary value, such as a rate or a percentage, to two decimals. Such a line is exempt when it carries the comment `/* not-money: <what it rounds> */` on the same line. Use the exemption only for values that §1 lists as out of scope.

    Adding a file to `pendingFiles` is only legitimate when a slice must keep a cent helper temporarily, for example a shared normaliser (§2). The PR body must state the reason, and the entry must be gone by R9.
  - **Runtime.** Each slice adds focused scenarios for the writers it migrates. The scenarios start from whole-yen balances and drive the slice's writers directly. The test asserts that every ledger row those writers produce has a whole-yen `amount` and whole-yen effects, and that the state fields they write are whole. This also covers writers that never had a cent helper (for example an unrounded `deposit*.6`), which the lexical ratchet cannot see. A full seeded run would also exercise unmigrated writers, whose fractions can legitimately cap a migrated amount (§3.5), so it is not used before R9. R9 empties `pendingFiles` and adds a fixed seeded full run. That run asserts that every ledger row is whole, and that every company, personal and competitor cash/debt field is whole.

## 10. Ordering with other Economic Engine work (Owner decision, 2026-10-22)

Economic Engine phases and this migration both rewrite authoritative money writers. To avoid conflicting edits, double work and failures whose cause cannot be told apart:

1. **Until R0 and R1 are `DONE`,** do not start or merge Economic Engine work that adds or changes a writer of cash, debt, ledger rows or settled amounts. Read-only work may continue in parallel: read models, projections, reconciliations that post nothing, contracts and tests that write no money.
2. **From the merge of R0,** every new or rewritten money writer, in any task, settles its amounts with `ceilYen` (and `allocateYen` for allocations), following §3–§4. This includes writers outside this migration.
3. **After R1,** Economic Engine work that changes a money writer in a file that a later slice still owns waits until that slice is `DONE`. If it cannot wait, it migrates the file to whole yen itself, under that slice's rules and acceptance checks, and marks the slice row (or a sub-row) `DONE` in the same PR.
4. Before you start any Economic Engine task, check §8 to find out whether the task writes money, and which slices it touches.

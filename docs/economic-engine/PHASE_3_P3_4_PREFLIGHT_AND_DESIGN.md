Removing compulsory adoption of arbitrary pre-existing metadata, historical lot repair and old-generation reconstruction reduces scope. Do not round share quantities to repair ownership; whole-yen rounding concerns settled money only (rounding contract §1).

## 3. Proposed authority adoption

### 3.1 One authority, existing backing fields first

**Proposal, not installed API:** introduce an ownership gateway for the player-company single common class, retaining the current source fields as the sole backing storage initially. Avoid a second persisted cap table plus mutable legacy roots. This follows P3-3 requirement 1 and the read-only snapshot architecture; it is not a promise to retain every old saved schema.

Proposed signatures:

```ts
inspectOwnershipAuthority(committedState, scope): OwnershipEvidence
planOwnershipChange(committedState, intent): OwnershipPlan | Rejection
applyOwnershipPlan(transactionEngine, plan): AppliedResult | false
```

`scope` identifies issuer/class/currentCompanySerial and adopted fact/family. `intent` includes existing operation/lifecycle ID, legal account, source lot keys, command kind, exact expected pre-quantities and prospective quantity deltas. Settled money is supplied by the existing rounded financial writer, not calculated/posted a second time by ownership. `plan` includes expected source revision/fingerprint, all quantity/mirror updates, legal-owner attribution and invariant checks. No host clock or RNG IDs. Proposed names are design choices, not assertions of existing exports.

Preflight is pure: invalid/nonfinite/out-of-envelope quantities, inconsistent issued/treasury/known-holder conservation, unsupported class/holder/generation, stale source or unadopted family returns a structured rejection without mutation/save. Share quantities are never ceilYen-rounded. Existing common-class/founder/source IDs and exact P3-2 conservation are retained. The residual stays unallocated evidence, never a fabricated external holder or fund voting grant (P3-3 family boundary).

Application is internal to an existing **active outer boundary**, never a standalone writer that calls save. Revalidate the plan against the same current state/shadow, update all adopted facts synchronously, then let the existing command finish financial/status/history work and the outer transaction commit once. A mismatched plan returns false so the enclosing transaction rejects. Exceptions propagate according to the existing command: engine TX rethrows after rollback; financed M&A catches and returns false. Do not flatten these behaviors into a new command contract without review.

Reuse engine.runTransaction / checkpointSaveStorage and the existing financed-M&A shadow. Pass the shadow engine/state explicitly; never capture the live engine in a helper executing on shadow. Existing checkpoint cancellation restores mirror/cache and cancels only newly admitted queued writes; it does not undo completed asynchronous IDB writes. Save true remains admission/enqueue. Finalization and commit-time emissions stay within their actual installed rollback region (001 correction report and §2 citations).

No authority `apply` from raw UI/ensure/projection; exported raw helpers either delegate to this gateway in their existing caller boundary or reject activation. LOAD/restore/refounding select or invalidate the authority view, never replay issuance. Cache invalidation must include same-week trade, IPO, split, rollback, SH replacement, hydrate/import and currentCompanySerial changes; week-only/object-identity caches are insufficient (cross-slice architecture §6–§7).
